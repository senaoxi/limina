# 为什么需要 Limina

一个 TypeScript 项目起步时，通常只需要一份 `tsconfig.json` 和一个类型检查命令。源码放在哪里、依赖什么、由谁检查，都容易看清。

仓库逐渐拆成多个包，同一个包又包含浏览器代码、Node 代码、测试和工具脚本后，这些问题开始分散到不同配置中。移动一个文件或增加一条导入，可能同时影响包依赖、类型检查范围和构建关系。

维护者需要持续判断：**源码里的实际关系，是否仍然符合包声明、检查配置和团队约定的边界。**

## 类型检查通过之后，还需要关心什么

假设一个工作区里的应用直接导入另一个包的源码：

```ts
// packages/app/src/main.ts
import { Button } from '../../ui/src/Button';
```

在允许直接解析工作区源码的配置下，这条导入可能通过类型检查，开发构建也可能正常。但它绕过了 `ui` 的公开入口；`app` 的 `package.json` 甚至可能没有声明对 `ui` 的依赖。

类型检查回答了当前程序中的类型问题。团队仍需判断：`app` 是否有权使用这个包，是否通过约定的入口访问，以及这样的访问能否在独立构建或发布后继续成立。

如果团队要求通过包入口访问，就需要在 `app` 中声明依赖，由 `ui` 暴露对应入口，再改为：

```ts
import { Button } from '@acme/ui';
```

这几处信息需要配合，但各自回答的问题不同：

| 信息                   | 回答的问题                                 |
| ---------------------- | ------------------------------------------ |
| 源码 `import`          | 这个文件实际使用了哪个模块入口？           |
| `package.json` 依赖    | 这个包声明可以使用哪些包？                 |
| `package.json#exports` | 这个包向使用方暴露哪些入口？               |
| `tsconfig`             | 哪些文件在什么类型环境中接受检查？         |
| TypeScript 项目引用    | 项目构建需要先构建并消费哪些上游项目输出？ |

改用包名只是其中一步。包声明、入口解析和类型构建关系仍然需要分别检查。

## 一个包内，也有不同的类型检查范围

包边界并不能表达所有源码约束。例如，一个包可能包含：

```txt
packages/example/
  src/client/   # 浏览器代码
  src/node/     # Node 代码
  src/shared/   # 两端共用的模块
  tests/        # 测试
  scripts/      # 工具脚本
```

假设团队希望 `client` 和 `node` 都可以依赖 `shared`，而 `shared` 保持运行时独立，`client` 也不能依赖 Node 专属模块。

这些范围可以分别使用适合自身类型环境的 `tsconfig`。测试和工具脚本同样需要检查，但它们的类型环境、可用依赖和生产源码未必相同；接受类型检查，也不意味着应该进入生产发布产物。

拆分配置之后，又出现了需要协调的关系：新增文件有没有进入预期的检查范围，某个文件是否同时被多个配置当作自己的源码，跨配置导入是否需要上游声明，以及依赖方向是否符合团队约定。

这里的“源码归属”指文件属于哪份配置选定的源码范围。`shared` 被客户端和测试同时导入，与它同时被两份配置列入各自的源码范围，是不同的关系；共享使用本身不等于归属冲突。

目录名称只能帮助人理解用途。要让工具报告违规，还需要把源码范围和允许的依赖方向写进配置。

## Limina 如何减少这些维护工作

Limina 读取源码配置与包声明，并使用类型检查器对导入和类型来源的分析结果，检查源码归属与依赖规则，为支持声明构建的检查器生成所需的项目引用。

团队负责决定边界，Limina 负责在已配置的范围内计算和检查它们。两项职责分别对应“哪些关系应该被允许”和“当前代码是否符合这些要求”。

### 检查源码归属和依赖边界

对于前面的例子，Limina 可以检查跨包相对导入、包导入是否获得依赖声明授权，以及纳入检查范围的源码是否存在检查遗漏或归属冲突。

运行时限制需要另外配置。例如，在客户端源码的 `tsconfig` 中应用相应的[图规则](./config/graph-rules.md)，限制它对 Node 内置模块或指定服务端源码范围的依赖。仅把目录命名为 `client`，不会启用这些限制。

这些检查帮助维护者在新增、移动或拆分源码时，发现代码与既定边界之间的偏差。

### 根据声明构建需求生成项目引用

TypeScript 的[项目引用](https://www.typescriptlang.org/docs/handbook/project-references.html)让项目通过声明输出建立依赖关系；配合 `tsc -b`，编译器可以按依赖顺序构建，并跳过已经是最新状态的项目。需要维护的是：引用关系是否仍然符合当前源码的构建需求。

在 Limina 中，团队继续维护描述源码范围和类型环境的配置。Limina 根据检查器对依赖及类型来源的分析，推导所需的项目引用，再交给 `tsc`、`tsgo` 或 `vue-tsc` 执行声明构建。

例如，`client` 导入 `shared` 中的模块时，如果两者分属已纳入检查范围的不同源码配置，且检查器表明当前构建需要 `shared` 源码提供声明，Limina 才会在满足归属和检查器兼容条件后生成对应引用。若检查器消费的是已有 `.d.ts`，这次消费本身不会产生对其源码的项目引用。

因此，源码导入、产物消费和项目引用需要分别解释。具体区别见[为什么导入不能直接等于引用](./why-import-is-not-references.md)。Astro 和 Svelte 检查器按各自的源码配置执行类型检查，不生成声明构建配置；框架检查之间的调度关系也不等同于 TypeScript 项目引用。

### 将检查延伸到配置的构建输出

源码阶段的关系正确，仍不足以说明发布后的包可以被使用。消费者读到的是包入口和构建输出，可能与工作区开发时直接访问的源码不同。例如，入口声明仍指向源码文件，发布包却只包含构建后的文件。

对于需要发布的包，可以在构建产物准备好后，配置[包检查](./config/package-checks.md)和[发布检查](./config/release-checks.md)。覆盖范围取决于所配置的输出、启用的检查和可用的分析工具；这些检查仍需配合真实消费者测试。

Limina 负责上述关系的推导与检查。包管理器仍负责安装依赖，类型检查器执行类型检查与受支持的声明构建，打包工具生成生产产物。业务行为、API 设计和边界是否合理，仍需要测试与评审。

## AI 辅助修改也需要结构反馈

AI 可以根据项目文档和 `AGENTS.md` 等指令修改代码，但也可能遗漏依赖声明、绕过包入口，或让新文件脱离预期的检查范围。这些改动需要与人工改动相同的检查。

将团队约束写成规则后，本地和持续集成中的 Limina 报告可以提供具体的文件、配置和依赖证据，帮助开发者或 AI 定位问题。

修正一条违规导入，与修改允许清单、忽略规则或边界例外，含义不同。后者改变了团队接受的约束，应由开发者审查理由，而不能仅以检查通过为目标。

## 什么时候值得接入

判断依据是结构关系的维护成本。出现以下情况时，可以考虑接入 Limina：

- 多份源码配置需要协作，文件归属和检查覆盖容易遗漏或重叠。
- 包依赖、公开入口和实际导入经常发生变化，评审需要反复检查它们是否一致。
- 团队已经有运行时边界或依赖方向约定，希望在本地和持续集成中持续检查。

如果项目只有清晰、稳定的源码范围，现有类型检查和构建流程已经足够，继续沿用它们也是合理选择。

接入需要团队明确源码范围、由哪个检查器负责，以及适用的边界规则，并处理已有配置中的冲突。Limina 可以减少重复维护，但不会替团队决定如何拆包、设计公开 API 或接受架构例外。

## 从现有项目开始

可以先围绕一个具体问题评估接入，例如检查遗漏的源码，或维护客户端与服务端的依赖边界：

1. 按[快速开始](./getting-started.md)准备依赖并初始化配置，核对哪些包和源码会纳入检查，以及每份源码配置由哪个检查器负责。
2. 如果实际包含源码的 `tsconfig` 已经手写 TypeScript 项目引用，按[迁移说明](./cli.md#limina-migration)使用匹配版本的 `limina-migrate` 处理。初始化不会改写源码 `tsconfig`，不能把初始化完成视为迁移完成。
3. 运行检查，结合报告中的文件、配置和依赖证据处理问题，再将适用的检查接入日常开发与持续集成。

阅读结果时，同时查看检查范围和执行状态：禁用、受阻、跳过或不可用的分析，都不能作为相应关系有效的依据。
