# 为什么需要 Limina

`TypeScript` 多包仓库一开始通常很简单：一个根 `tsconfig.json`，几个包，再加一个类型检查脚本。

这时通常可以直接看出文件属于哪个包、依赖哪些模块、由哪个配置检查，以及构建时的依赖顺序。

仓库增长后，一个包可能包含浏览器代码、`Node` 代码、共享模块、测试、工具、构建配置和发布入口。这些源码范围往往需要不同的类型环境和各自的 `tsconfig`。

配置增多后，还需要维护它们之间的 `TypeScript` 项目引用。需要声明的源码依赖发生变化时，构建顺序可能随之变化；运行时边界和检查覆盖范围也需要检查。

Limina 读取源码配置和检查器提供的依赖事实，生成受支持的声明引用，并检查已配置的源码归属和依赖规则。

## 一个包也可能是一组工程边界

在简单项目里，包通常可以被理解成一个边界：一个包、一组源码、一个类型检查入口。

但在复杂 `TypeScript` 多包仓库中，一个包内部可能已经包含多组边界。例如，一个 `VitePress` 相关包可能同时包含：

- 面向浏览器的客户端运行时代码。
- 面向 `Node` 的服务端或构建时代码。
- 浏览器和 `Node` 都可能复用的共享模块。
- 测试代码。
- 构建脚本和工具脚本。
- 面向使用方发布的多个公开入口。

同包文件也可能需要不同的类型环境。例如，项目可能要求浏览器代码不依赖 `Node` 内置模块，共享模块不绑定某个运行时，测试和工具代码不进入生产构建关系。

不同的 `tsconfig` 可以表达这些类型环境，但配置之间的依赖关系仍需要维护。

## 项目引用增强了构建，也增加了维护成本

`TypeScript` 项目引用适合大型仓库。它可以让类型构建按依赖顺序执行，并复用增量构建结果。

但项目引用的前提是：引用图必须准确。

跨包访问和[同包内的不同源码范围](#一个包也可能是一组工程边界)都可能涉及项目引用。例如，同包内的相对导入：

```ts
import { resolveThemeConfig } from '../shared/theme';
```

只有导入方和目标文件属于不同的受管配置，且检查器的语义证据要求源码声明提供者时，生成的声明构建才需要对应项目引用。消费已有声明产物或观察到框架调度依赖，本身不要求该引用。

手动维护引用时，需要检查源码所属配置，按依赖变化增删引用，并确认是否违反运行时边界。

配置越多，保持声明依赖和构建引用一致的工作也越多。引用一致有助于按依赖顺序构建和复用增量结果；源码覆盖和运行时边界仍需要独立检查。

## Limina 从项目引用图开始治理

Limina 在受支持的声明构建中使用 `TypeScript` 项目引用。

团队仍然维护源码配置和包边界。Limina 读取这些配置与检查器推导的依赖事实，为支持构建的检查器生成声明构建关系，并按已配置的治理规则检查这些关系。Astro 和 Svelte 检查器按叶子配置执行，没有声明配置投影；产物消费单独导出，不证明构建任务顺序。

Limina 根据当前配置和依赖事实重新计算声明引用，减少手动维护。生成图可以通过本地命令和持续集成检查。

源码结构变化后，Limina 检查声明提供者需求、已配置的运行时规则、源码归属和检查覆盖范围，并生成供受支持检查器执行声明构建的引用。

以下场景说明这些检查的用法。源码归属、声明引用、框架调度和产物消费仍是不同事实，不会全部变成 TypeScript 项目引用（`references`）。

## 典型场景：同一个包支持多个运行时

假设一个包同时包含 `client`、`node` 和 `shared` 三类源码：

```txt
packages/example/
  src/client/
  src/node/
  src/shared/
```

通常它们会分别有不同的类型环境：

```txt
src/client/tsconfig.json   # 浏览器运行时
src/node/tsconfig.json     # Node 运行时
src/shared/tsconfig.json   # 共享模块
```

本例假定 `client` 可以依赖 `shared`，但不应依赖 `node`；`shared` 需要保持运行时独立；`node` 可以使用 `Node` 类型和内置模块。

这些要求需要通过源码范围和图规则表达。跨配置导入还需要检查声明引用，见[项目引用增强了构建，也增加了维护成本](#项目引用增强了构建-也增加了维护成本)。

用户声明源码归属范围和图规则。Limina 根据源码依赖构建受支持的声明图，并报告规则违规。仅有 `client` 或 `node` 等目录名称不会建立运行时规则。

## 典型场景：测试和工具代码不应污染主构建

复杂包中还经常包含测试代码和工具脚本：

```txt
packages/example/
  src/
  scripts/
  tests/
  vitest.config.ts
  build.config.ts
```

这些文件需要类型检查，但它们不一定应该参与生产产物构建。负责测试或工具配置的构建型检查器，仍可以通过 Limina 的声明构建检查自身范围。

测试可能使用仅测试可用的依赖，工具脚本可能使用 `Node` 专属模块。用独立配置区分它们与生产源码的类型环境，做法与[多运行时示例](#典型场景-同一个包支持多个运行时)相同。

按用途配置源码归属：测试文件进入测试配置，工具脚本使用合适的类型环境，生产源码不归测试或工具配置所有。

归属检查可以报告同一文件被多个配置覆盖的冲突。

## 典型场景：代码能跑，但结构已经不可预测

跨包相对导入是多包仓库中常见的结构问题：

```ts
import { Button } from '../../ui/src/Button';
```

这条导入绕过了包名、依赖声明和公开入口。即使代码可以解析，`package.json` 也可能没有声明这条依赖。

在导入方包中声明依赖，并通过公开入口访问：

```ts
import { Button } from '@acme/ui';
```

Limina 可以根据依赖声明和被消费的公开入口检查这条导入。声明提供者边、框架调度或产物消费仍取决于检查器事实和目标归属；仅使用包名不能建立项目引用。

`#imports` 也遵守这个思路：相对目标是声明它的包作用域内部入口，不能借它访问其他包；包目标可以指向三方包或工作区依赖，但仍然需要由导入文件所属的源码归属方授权。

与[同包内跨配置导入](#项目引用增强了构建-也增加了维护成本)一样，解析成功本身不能证明源码归属、导入授权或声明引用要求已满足。

## AI 迭代让结构反馈更重要

代码修改可能绕过包入口、遗漏依赖声明，或让源码脱离预期的检查范围。维护者除了审查改动本身，也需要检查这些关系。

由 `AI` 生成的改动也需要同样的审查。能写成检查规则的约束，可以减少重复的人工检查。

文档、任务说明，以及 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules` 等项目指令，可以向 `AI` 说明仓库规则。仍需要通过检查结果发现遗漏或误解。

类型检查、静态分析和格式检查可以提供可重复的问题报告，`AI` 可以据此修复类型、语法和代码风格问题。

导入绕过包入口、依赖未声明或源码脱离预期检查范围时，局部类型或风格检查仍可能通过。

Limina 检查已配置的源码归属、项目引用、包边界和覆盖范围。业务行为仍需要测试、评审和领域验证。

这些检查可以在本地、持续集成或拉取请求流程中运行，与其他验证结果一起提供结构问题报告。

`AI` 可以根据检查结果修复普通违规，但涉及允许清单、忽略规则、边界例外或需要 `reason` 的变更，更适合由开发者确认。因为这些变更通常不是普通修复，而是在声明团队接受某个架构例外。

审查 `AI` 辅助修复时，应区分各项检查的范围：测试验证业务行为，常规工具提供类型和静态规则反馈，已启用且完成的 Limina 检查验证所配置的归属和架构规则。

## 最终目标：降低结构维护成本

Limina 希望减少声明引用和源码边界的人工维护。

多个包、运行时、检查器和发布入口需要一致的归属与依赖配置。前面的示例分别说明了运行时范围、测试和工具配置，以及跨包访问。

已配置的检查可以帮助回答：

- 这个文件属于哪个源码范围？
- 它应该由哪个 `tsconfig` 管辖？
- 它依赖的模块是否符合运行时边界？
- 项目引用是否准确表达了真实源码依赖？
- 类型构建图是否可以增量执行？
- 测试、工具和生产源码是否被清晰分离？
- 发布前产物是否仍然符合源码阶段建立的结构预期？

每项结果都应按配置范围和已完成的检查解释；禁用（`disabled`）、受阻（`blocked`）、跳过（`skipped`）或不可用的分析不能证明相应关系有效。包检查和发布检查需要已配置的构建输出，并仅作为真实消费者测试的补充。

可以根据报告中的配置路径、文件和依赖证据，定位并修正未通过检查的关系。
