# Getting Started

Adopt Limina by installing it, initializing a config, migrating when needed, and running the first check. This produces source-structure and type-check results; the project's production artifacts are still generated by its build workflow.

## Requirements

Limina supports single-package projects and pnpm, npm, Yarn, and Bun workspaces. The configuration examples below use ESM.

- Node.js `^22.18.0 || >=24.11.0`.
- A readable `package.json` whose top-level value is an object.
- TypeScript within the installed Limina release's peer dependency range. The current source version supports `>=5.4.0 <5.10.0 || >=6.0.0 <6.1.0`.

Vue, Astro, and Svelte also require their corresponding checker dependencies. See [Checker Configuration](./config/checkers.md#framework-prerequisites) for where to install them and which generation steps must run first.

## Install

If the project already has a compatible TypeScript version, keep it and install Limina:

::: code-group

```bash [pnpm]
pnpm add -D limina
```

```bash [npm]
npm install -D limina
```

```bash [yarn]
yarn add -D limina
```

```bash [bun]
bun add -d limina
```

:::

If TypeScript is not installed, add a version within Limina's peer dependency range. For the current source version, using pnpm:

```sh
pnpm add -D typescript@~6.0.3
```

For other Limina releases, use the compatibility range declared by that release. The native `tsc` checker uses the TypeScript resolved by Limina itself; another `tsc` on `PATH` or in a package directory does not override it.

## Pick an Adoption Path

If no Limina config exists, use the initialization workflow below or write a [minimal manual config](#minimal-manual-config). Both approaches leave source scopes and type environments under your control. Existing source project references may need a separate migration.

## Initialize an Existing Project

Run this in the project directory you want to adopt. The remaining commands use pnpm:

```sh
pnpm exec limina init
```

Initialization searches upward from the current directory for the nearest `package.json` and writes the config beside it. An invalid nearest manifest stops initialization; a manifest creation flow is offered only when the entire ancestor chain has no package manifest. Initialization does not add workspace declarations.

Initialization may create or update:

- `limina.config.mts`, with automatic checker discovery enabled and `auto.exclude` initially set to `[]`;
- `.limina/` in `.gitignore`;
- the `limina:build` script in `package.json`, set to `limina checker build`;
- missing `limina` and `typescript` development dependencies.

`limina:build` runs Limina's internal declaration build, not the project's production bundling command. Initialization can also install the optional Limina agent skill if selected.

::: warning Review existing content before initializing again
Initialization deletes the root `.limina/` directory, including generated files and persisted check and migration records. `--yes` accepts core initialization confirmations, including overwriting an existing config or a conflicting `limina:build` script, and skips optional skill installation.
:::

For non-interactive use:

```sh
pnpm exec limina init --yes
```

Reinstall dependencies as prompted only if initialization changed dependencies or created a package manifest:

```sh
pnpm install
```

`--yes` can also complete without package-manager metadata; the subsequent guidance then remains package-manager-neutral. For manual installation of the optional skill, see [the init command](./cli.md#limina-init).

### Migrate Existing Project References First

Initialization does not rewrite source tsconfigs. If configs that actually contain source still declare native `references` by hand, first install the separate `limina-migrate` package at the same version as `limina`, then run:

```sh
pnpm exec limina-migrate
```

Review the migration result before running checks. Migration only establishes input configs that can be read again; it does not mean full governance or checker execution has passed, and it does not guarantee equivalence to native `tsc -b`. See [Migration](./cli.md#limina-migration) for eligibility, write scope, and result locations.

## Run the First Check

```sh
pnpm exec limina check
```

The default pipeline includes:

| Task                | Main responsibility                                                         |
| ------------------- | --------------------------------------------------------------------------- |
| `graph:check`       | Declaration references, actual imports, and configured graph rules          |
| `source:check`      | Source ownership, package import authorization, and enabled source analysis |
| `proof:check`       | Coverage of source expected to be checked                                   |
| `checker:build`     | Declaration builds with `tsc`, `tsgo`, and `vue-tsc`                        |
| `checker:typecheck` | Type checking for Astro and Svelte source configs                           |

This is report order; tasks may run concurrently when concurrency limits and resource locks allow it. The command generates checker configs under `.limina/` as needed and runs the actual checkers. It does not build every package's production artifacts or include package and release checks.

Also inspect execution status. When there are no framework checking targets, `checker:typecheck` is `disabled`; disabled, blocked, and skipped work is different from a passed check. See [Built-in Tasks](./built-in-tasks.md) for responsibilities and status meanings.

On failure, start with the task, issue code, and file path in the output. To read issues from a completed run again:

```sh
pnpm exec limina check --issues
```

`--issues` reads saved results without rerunning checks. An incomplete attempt or an unavailable record does not mean zero issues. See [Troubleshooting](./troubleshooting.md#identify-the-failing-task) for narrowing the scope and handling different failures.

## Governance Root

The selected config determines the checking scope. Limina searches upward from that config module for the nearest `package.json` and uses its directory as the governance root. Only that root's own workspace declarations determine membership; without workspace declarations, the run is treated as a single-package project.

### Selecting a Config Inside a Monorepo

Selecting the repository root config checks its workspace. Selecting a child package's own config uses that package's nearest manifest; ancestor workspace declarations do not automatically widen the scope. When running from a subdirectory, explicitly select the intended config:

```sh
pnpm exec limina --config ../../limina.config.mts check
```

Adjust the example path to the current directory. See [Config File](./config/config-file.md) for discovery order, package-manager authority, and path resolution.

## Minimal Manual Config

Create `limina.config.mts` beside the selected project's `package.json`:

```ts
import { defineConfig } from 'limina';

export default defineConfig({
  config: {
    checkers: {
      auto: {},
    },
  },
});
```

Automatic discovery is always enabled. Limina finds default `tsconfig.json` entries in activated package scopes, then follows aggregator `references` to source configs. `auto.exclude` can exclude automatically discovered entries, but it does not cut references reached from an entry already selected. See [Checker Configuration](./config/checkers.md) for the full selection rules.

After manual configuration, run `pnpm exec limina check` as well. If you want a separate declaration-build script, add:

```json
{
  "scripts": {
    "limina:build": "limina checker build"
  }
}
```

## Configure Checker Ownership

Start with automatic discovery in most cases. Add a named scope only when certain entries need a fixed checker:

```ts
import { defineConfig } from 'limina';

export default defineConfig({
  config: {
    checkers: {
      'vue-tsc': {
        include: ['packages/web/tsconfig.json'],
      },
    },
  },
});
```

Entries not claimed by named scopes continue through automatic discovery. `include` selects only default `tsconfig.json` entries. Named source configs such as `tsconfig.lib.json` and `tsconfig.test.json` must be referenced by an aggregator entry, not placed directly in a selector. See [Core Concepts](./concepts.md#aggregator-config) for the distinction.

Relationships that need declaration output also require compatible checker ownership; interdependent source scopes cannot arbitrarily be fixed to different build checkers. Astro and Svelte configs run type checking only. Application builds and prerequisites such as framework-generated types remain part of the project workflow.

After the first check, follow [Workflows](./workflows.md) to add checks to local development and CI. Configure artifact checks when you need to publish packages.
