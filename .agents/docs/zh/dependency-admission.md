# 依赖准入

[English](../dependency-admission.md) | [简体中文](./dependency-admission.md)

本记录定义仓库在需求分析阶段评估第三方复用，以及新增、替换和更新 npm 依赖时采用的准入政策。

本政策约束候选选择与引入方式。未经单独审查，不自动判定所有现有依赖合规或不合规。已经通过准入的包，其后续版本、新用途和新增执行权限不自动获得批准。

政策区分硬性准入门槛与比较信号。任何硬性门槛明确失败，候选均不得引入；关键证据不足时，应标记为待评估，而不是默认通过。比较信号只用于选择已经通过全部适用门槛的候选。

## 评估对象与范围

准入对象是具体的包、精确版本、发布来源、使用方式及其实际解析结果，不是对某个包名或上游项目作永久背书。

评估应说明依赖将声明在哪个 workspace package 中，使用哪些 API 或入口，在安装、构建、测试、发布和运行中的哪些阶段执行，以及需要支持哪些环境。

安全、来源、许可证和兼容性审查应覆盖本次变更新增或改变的相关传递依赖，包括适用环境中实际安装、执行或分发的 optional dependencies、peer dependencies、原生组件和预构建二进制。

必要性、生态采用情况和整体维护成本按候选方案评估，不要求对每个传递依赖重复进行完整选型。人工审查深度应与执行权限、输入可信度、分发范围和替换难度相称。

将第三方代码复制、vendoring 或打包进仓库，不免除来源、许可证、安全和维护责任。通过临时执行工具而不写入 package.json，也不得绕过来源和执行安全审查。

## 需求分析与复用

分析需求或规划自行实现前，先检查现有平台、workspace 和工具链能力，再检查合适的开源包是否能够直接满足需求，或通过边界明确的适配满足需求。

先定义所需行为和不可退让的约束，再比较候选。比较内容应包括正常行为、失败语义、输入边界、资源生命周期、兼容性、集成范围及长期维护成本。不能仅因包的描述与需求相似，就认定其行为等价。

优先复用满足本记录要求且长期成本合理的第三方包。复用优先不豁免任何硬性门槛，也不要求为适配第三方抽象而扩大需求、改变既有架构边界或削弱仓库约束。

如果仓库只需要某个包中很小、稳定且边界明确的能力，并且本地实现能够以更低的长期成本被理解、测试和维护，应优先实现最小所需能力，而不是接受整个包的依赖和升级范围。

采用本地实现时，应说明评估过哪些合理候选，复用或适配为何不足或成本更高，以及本地实现支持和不支持的行为。不要求穷举全部生态候选，但不能跳过明显适用的现有能力。

不要仅为减少依赖数量，就自行替换成熟的密码学、安全机制、协议、parser、标准兼容实现或其他高风险行为。使用代码行数或功能点数量，不能代替对语义复杂度和维护成本的判断。

借鉴或复制第三方实现时，必须核查许可证、署名和再分发义务。复制后的代码应保留来源、采用的版本或 commit、必要 notices，以及后续修复责任。

未能证明必要性的候选不能通过准入。

## 准入顺序与证据

按以下顺序评估候选：

1. 明确需求、使用边界、验收条件及现有能力不足的原因。
2. 检查来源、许可证、废弃状态和已知风险，排除明显不合格的候选。
3. 在受控环境中验证实际发布包的功能、兼容性、执行行为和成本。
4. 比较通过全部门槛的候选，选择满足需求且长期依赖与维护成本最小的方案。

证据应对应拟采用的版本。发布包内容、对应版本的源码与测试、官方文档、registry 信息及可复现验证结果应相互核对；不能用当前主分支的行为证明某个已发布版本具备相同能力。

记录检查日期、版本、来源及关键命令和结果。源码阅读不等于运行验证；没有执行的检查、无法访问的数据和未覆盖的环境必须明确标注。

低风险依赖可以使用简短的准入摘要。涉及不可信输入、敏感数据、高权限执行、安装下载、原生组件或核心公共接口的依赖，应提供与风险相称的额外验证。

## 功能、兼容性与集成边界

候选必须满足已定义的必要行为，并与仓库声明支持的环境兼容。适用范围包括 Node.js、模块格式、TypeScript、browser、framework、操作系统、CPU 架构及必要的系统库。

验证应覆盖实际使用的入口、配置和失败路径。安装成功、类型检查成功或 README 示例成功，均不能单独证明集成正确。

需要类型支持时，应确认类型声明与实际 API 一致，并能在仓库支持的编译和模块解析模式下使用。不得依靠未声明的 workspace 依赖、意外提升的依赖或开发环境中的额外文件才能工作。

优先依赖上游明确支持的公开 API。需要使用未承诺稳定的内部接口、深层路径、补丁或 fork 时，应单独说明必要性、升级风险和维护责任；不能将其成本隐藏在普通适配中。

只有在确实能够隔离外部类型、错误模型、资源生命周期或替换成本时，才增加内部适配层。不要求为每个简单调用创建无实际作用的 wrapper。

引入候选不得隐式缩小仓库已有支持范围。需要提高最低运行时版本、移除平台支持或改变公共接口时，应作为独立的兼容性决策审查。

无法满足必要语义或支持边界的候选不能通过准入。

## 来源与供应链

必须核对包名、scope、registry、项目仓库和发布者之间的关系，确认拟安装的是预期项目发布的版本。不能仅凭相似名称、下载量或组织名称认定来源可信。

审查应以实际分发的包为对象，检查必要的入口文件、许可证、安装脚本和附带组件。源码与发布包不要求字节相同，但构建、生成或打包造成的差异应能够解释；异常内容或来源冲突未解决前不得通过。

依赖解析结果应由仓库采用的 lockfile 和完整性校验机制固定。完整性校验只能证明取得的内容符合记录，不能单独证明代码可信。

候选提供 registry 签名、provenance 或可信发布信息时，应按可用工具验证，并核对预期来源。存在且应当有效的验证材料校验失败时，不得忽略失败继续引入。

缺少 provenance 本身不是普遍的否决条件，但应结合包的风险、发布历史和其他来源证据作出判断。来源无法合理确认时，应暂停准入。

安装或运行过程中额外下载的二进制、脚本和其他可执行内容，应纳入同一审查范围，并具有明确来源、版本固定或内容校验机制。

遵守仓库现有的发布冷却期、registry 限制、脚本审批和信任策略。不得为了安装某个候选而静默关闭全局保护。

## 安全与执行行为

必须检查拟采用版本及相关传递依赖的已知漏洞、安全公告和恶意包报告，并说明实际使用方式是否满足漏洞触发条件。

已确认恶意或被篡改的版本不得引入。适用于仓库且尚未有效修复或缓解的高危、严重漏洞不得通过准入；不能仅以尚无修复版本为理由接受。

其他已知漏洞也必须完成评估，记录影响、可利用条件、现有保护和剩余风险，并由负责审查的维护者明确决定。存在适用且兼容的修复版本时，应优先采用修复版本。

数据库命中不等于漏洞必然可利用；无告警也不等于没有安全风险。声称漏洞不适用或已被缓解时，必须提供与漏洞机制相关的证据，不能仅以“生产代码没有直接 import”为依据。

审查范围包括安装、构建、测试和发布环境。纯开发依赖只可能不适用生产体积门槛，不豁免安全、来源、许可证和维护要求。

候选所需的文件读写、网络访问、子进程、动态执行、遥测和凭据访问，应与其用途相称并符合仓库边界。不可解释、不可控制或与用途无关的高风险行为，应阻止准入。

需要执行安装脚本或其他初始化代码时，应先审查其必要性，再按最小范围授权。首次验证未经审查的执行行为时，不得提供生产凭据、发布权限或其他无关敏感能力。

忽略告警、放行脚本或排除冷却期，不等于解决了底层风险。任何此类配置都应具有明确范围、理由、责任人和重新检查条件。

## 许可证兼容性

候选必须具有明确的授权依据，并与仓库的使用、修改、发布和分发模式兼容。

优先从[支持的许可证列表][supported-licenses]中选择宽松许可证，该列表与 bundled-code 许可证门禁共享。必须识别适用的 notices、署名、修改说明、专利条款及再分发条件，并确保仓库能够履行。

许可证审查应覆盖实际采用版本的分发包、对应源码及随之分发的相关组件。上游当前主分支的许可证不能自动代表历史发布版本；父包的许可证也不能替代其所包含第三方代码的许可证。

对多许可证表达式，应区分可选择的授权与需要同时履行的义务，记录实际采用的授权路径。扫描工具无法识别许可证时，应核查原始授权文件，不能仅凭 unknown 标签判定不存在许可证，也不能默认许可兼容。

许可证缺失或含糊、同一版本的授权信息存在未解决冲突、授权与预期用途不兼容，或仓库无法履行义务时，候选不能通过准入。

Agent 不得默认为互惠、源码披露或其他非宽松许可证开设例外。采用此类授权前，应说明具体义务并获得维护者明确审查；批准不能替代许可证兼容性和履约要求。

需要随产物提供的许可证和 notices，应纳入发布流程，不得只保存在准入讨论中。

## 废弃版本与维护状态

拟直接采用的精确版本不得在 npm registry 中标记为 deprecated。被废弃的直接候选版本立即准入失败，不参与比较。

不能仅因无关历史版本曾被废弃就拒绝整个项目，前提是选定版本仍受支持，且废弃理由不适用于它。应记录选定版本、检查日期、废弃状态及维护者提供的替代建议。

新增或改变的传递依赖出现 deprecated 标记时，必须检查废弃原因及实际影响。涉及安全、停止维护或不受支持的兼容性边界时，应按相应门槛处理；仅有迁移或重命名提示时，应记录判断依据，不能直接忽略，也不自动等同于整个方案不合格。

不能通过增加包装包或其他间接引入方式，规避本来应作为直接候选审查的废弃实现。

候选必须具有与其风险相称的维护可信度。应结合所采用版本线的支持状态、有效问题的处理、兼容性和安全修复、测试、发布来源及可识别的维护责任进行判断。

发布频率、issue 数量和维护者人数都不能单独决定准入。成熟包可能很少需要发布；单维护者项目或 0.x 版本也不因此自动失败。

项目归档或长期无发布时，应先确认是否迁移、是否功能已稳定，以及是否仍有可信的修复和发布途径。明确停止维护且没有可信接续，或关键安全、正确性和兼容问题长期无人处理时，不得准入。

其他条件相当时，优先选择维护响应更及时、发布过程更稳定、升级路径更清楚的候选。

## 生产产物与其他成本

生产体积门槛适用于实际进入或构成浏览器、client、edge、server、CLI 或其他交付产物的依赖，不以 package.json 中的字段名称单独判断。

评估前应固定交付单元、受影响入口、基线版本及测量口径。不得使用无关应用、workspace package 或静态资源的体积稀释本次引入的影响。

以引入前的可比生产构建为基线：

    absolute increase = size after introduction - baseline size
    relative increase = absolute increase / baseline size

同时记录基线体积、引入后体积、绝对增量和百分比增幅。两次测量必须使用相同的生产配置、入口、工具版本、优化设置和压缩口径。

测量实际生成或交付的产物，而不是使用 npm 页面上的包体积替代。浏览器场景应说明初始加载与按需加载的影响；server 和 CLI 场景应计入实际需要交付的外置依赖、资源和原生组件。

对发布到 npm 的库，还应分别记录自身 packed/unpacked size、相关安装依赖增量，以及适用时的代表性消费者构建结果。不得用自身 tarball 很小来证明消费者成本很低，也不得把安装体积直接当作浏览器 bundle 增量。

适用以下生产体积政策：

| 相对增幅           | 处理                                                                          |
| ------------------ | ----------------------------------------------------------------------------- |
| 低于 15%           | 不因该体积指标降低候选权重                                                    |
| 15% 至 30%，含两端 | 降低权重；接受前评估更窄的 imports、tree shaking、lazy loading 或更小替代方案 |
| 超过 30%           | 准入失败，不得以其他比较信号抵消                                              |

阈值适用于候选及其新增可达传递依赖带来的实际增量。替换方案按完整替换后的净变化评估；仍被其他用途需要的旧依赖，不能假定已经移除。

同一功能所必需的一组依赖应整体评估，不得通过拆分变更规避阈值。多个独立交付单元分别评估，不用平均值掩盖某个单元的超限。

相对阈值不能替代仓库已有的绝对体积、启动时间、内存或其他性能预算。违反适用预算的候选仍不能通过。基线为零或不存在可比交付单元时，不得把增幅记为零；应先确定经仓库认可的测量基线或独立预算，再作准入决定。

未进入交付产物的纯开发依赖不适用生产体积比例门槛，但仍应评估安装与下载成本、CI 时间、缓存、原生构建和日常开发负担。

## 比较信号

通过全部适用门槛后，比较候选满足需求的方式、适配复杂度、升级难度、依赖范围和长期维护成本。超出当前需求的功能不自动构成优势。

npm 周下载量是生态采用的方向性信号。在用途、能力范围和其他关键条件具有可比性时，持续较高的下载量提高候选权重。

记录统计来源、起止日期和当前完整统计周，并在数据可用时检查近期趋势。不要只使用异常周，也不要把下载量直接解释为独立用户数、代码审查人数或某个新版本已经得到充分验证。

下载量没有独立的通过阈值，无法取得下载量数据本身不构成硬性失败。Stars、社区讨论、知名项目采用情况和安全评分同样只作辅助证据，不能覆盖来源、安全、许可证、兼容性或其他门槛失败。

生产体积增幅为 15% 至 30% 时必须降低权重。其余条件相当时，优先选择维护更可靠、集成更简单、升级和退出成本更低的候选。

不采用未经校准的综合分数替代逐项判断；下载量优势不能自动抵消明显更高的适配、运行或维护成本。

## 引入验证与决策记录

准入前应对拟采用的发布版本完成与风险相称的安装、功能、兼容性和构建验证，并保留关键回归测试。复用既有测试和 CI 能力，不为每个依赖重复建立独立流程。

依赖应声明在实际使用它的 workspace package 和适当字段中。不能依赖未声明的传递依赖，也不能通过错误地放入 devDependencies、optionalDependencies 或 peerDependencies 隐藏实际运行要求和消费者成本。

提交与引入相匹配的 manifest、lockfile、必要配置和测试。验证应遵守仓库已有的包管理器、版本策略及可复现安装规则。

发布库或工具时，应根据风险执行独立的消费或安装测试，避免 workspace 环境掩盖缺失依赖、错误 exports、类型声明引用或发布文件遗漏。仓库自己的 lockfile 和根级 override，不能被视为下游消费者必然获得相同解析结果的保证。

准入记录可写入相关 PR 或既有决策记录，不要求另建重复台账。至少说明：

| 项目           | 必要内容                                                       |
| -------------- | -------------------------------------------------------------- |
| 需求与替代方案 | 所需行为、现有能力不足、评估过的合理候选及本地实现取舍         |
| 候选与用法     | 包名、精确版本、来源、声明位置、入口和执行阶段                 |
| 门槛结论       | 来源、安全、许可证、废弃状态、维护及兼容性结论；不适用项的理由 |
| 依赖变化       | 相关传递依赖、脚本、二进制、peer 或 optional 要求及重要变化    |
| 验证与成本     | 命令、实际结果、测量基线、绝对和相对增量、未覆盖范围           |
| 最终决定       | 选择理由、必要限制、维护责任人或团队，以及重新检查条件         |

有长期影响的适配、补丁、fork、override 和安全告警忽略，应记录其目的、适用版本、上游修复情况及退出条件。不能只留下没有解释的配置项。

## 持续复审

准入是有范围的当前判断，不是对未来版本的自动批准。常规更新可以复用仍然有效的需求和架构结论，但必须检查相关版本与依赖变化，并重新执行适用验证。

出现以下变化时，应重新审查受影响的结论：发布者或来源变化、许可证变化、新增安装或下载行为、依赖范围显著扩张、支持环境变化、关键 API 或公共类型变化、新的安全公告、deprecated 标记，或维护可信度下降。

使用方式变化也可能触发重新审查，例如从仅处理可信输入变为处理外部输入、从开发阶段扩展到生产执行，或新增访问凭据、网络和发布权限。

发现无关的存量问题时，应单独记录并安排处理，不自动扩大本次变更范围。但本次变更新增或放大的风险，不能以该依赖原本已经存在为理由豁免。

移除或替换依赖时，应同步清理不再需要的声明、适配代码、补丁、授权配置、告警忽略和发布材料；仍有其他使用方的内容不得误删。

## 决策摘要

硬性门槛包括：依赖具有可证明的必要性；必要语义和环境兼容性成立；来源可信；安全与执行行为符合本记录要求；许可证明确、兼容且能够履行；直接选定版本未 deprecated；维护状态可信；适用的生产体积与其他既有预算未被突破。

通过全部门槛后，才使用生态采用情况、生产体积增量、维护响应和长期总成本比较候选。

明确失败的候选不得引入。关键证据不足的候选保持待评估。只有确实不适用的条目才能标记为不适用，并说明理由。

没有候选通过时，应报告未满足的需求及可用替代方案。本地实现仍须满足必要性和风险边界，不能作为自动 fallback。

Agent 不得静默放宽门槛、隐藏告警或修改全局保护以使候选通过。确需调整政策时，应单独提出政策变更并获得明确决定，不能将其隐藏在依赖引入中。
