# 依赖准入

[English](../dependency-admission.md) | [简体中文](./dependency-admission.md)

本记录定义仓库范围内评估新增第三方 npm 包或替换已有包的政策。它约束候选选择；未经单独审查，不自动判定所有现有依赖合规或不合规。

政策区分硬性准入门槛与加权比较信号。未通过任一硬性门槛的候选不得加入。加权信号只用于比较已经通过全部门槛的候选。

## 准入顺序

按以下顺序评估候选：

1. 建立依赖确有必要的证据。
2. 排除未通过硬性门槛的候选。
3. 按生态采用情况、生产产物影响和维护活跃度比较剩余候选。
4. 优先选择满足所需能力，同时长期依赖和维护成本最小的候选。

## 必要性

第三方包必须解决具体需求，而仓库无法通过现有平台、workspace 或工具链能力合理满足该需求。

如果仓库只需要某个包中很小、稳定且边界明确的能力，应优先在本地实现最小所需能力，而不是接受整个包的依赖、升级和供应链范围。

只有当本地实现的行为能够以低于引入依赖的长期成本被理解、测试和维护时，本地实现才合适。不要仅为避免依赖，就用非正式的本地实现替换已有的安全敏感算法、协议、parser、标准或其他高风险行为的第三方实现。

借鉴第三方实现时，必须遵守其许可证和署名要求。除非许可证允许且仓库能履行由此产生的全部义务，否则不得将其源码复制到仓库。

未能证明必要性的包不能通过准入。

## npm 周下载量

npm 周下载量是加权的生态采用信号。在其他条件均可接受的候选中，持续较高的周下载量获得更大权重，因为它表示更广泛的安装基础，以及更可能遇到兼容性或正确性问题的更大用户群体。

不要只用某一个异常周作为比较依据。记录当前周下载量，并在数据可用时检查近期趋势。下载量没有独立的通过阈值，也不能覆盖未通过的硬性门槛。

高下载量不能证明包安全、许可证正确、维护活跃或适合本仓库。

## 生产产物影响

本标准仅适用于会进入浏览器、client、edge、runtime 或其他最终生产产物的依赖。不进入交付产物的纯开发依赖不适用。

以引入依赖前的生产构建为基线衡量候选：

```text
artifact increase = (size after introduction - baseline size) / baseline size
```

两次测量必须使用相同的生产配置、入口、优化设置和压缩口径。测量实际生成的产物，而不是包的安装体积。

适用以下政策：

- 增幅低于 15% 时，不因体积降低候选权重。
- 增幅为 15% 至 30%（含）时，降低候选权重。接受前应评估更窄的 imports、tree shaking、lazy loading 或更小的替代方案。
- 增幅超过 30% 时，准入失败，不得考虑该包。

体积阈值适用于该包及其新增可达 transitive dependencies 带来的增量影响。

## 许可证兼容性

候选必须声明明确的许可证，且与仓库的使用、修改、发布和分发模式兼容。

优先选择宽松许可证，包括 MIT、ISC、BSD-2-Clause、BSD-3-Clause 和 Apache-2.0。必须识别所有必要 notices、署名、专利条款或再分发条件，并确保仓库能够履行。

出现以下任一情况，包不能通过准入：

- 许可证缺失或含糊不清；
- npm metadata、源码仓库和分发包提供相互冲突的许可证信息；
- 许可证与仓库预期用途或分发方式不兼容；或
- 仓库无法履行其义务。

Agent 不得将互惠、源码披露或其他非宽松许可证作为隐含例外接受。应向用户说明许可证及其义务。

## 废弃版本

拟安装的精确版本不得在 npm registry 中标记为 `deprecated`。

被废弃的候选版本立即准入失败，不得参与加权比较。不能仅因无关历史版本曾被废弃就拒绝整个包，前提是选定的当前版本仍受支持，且废弃理由不适用于它。

评估候选时，记录选定版本、其废弃状态，以及维护者发布的替代建议。

## 维护状态

候选必须具有可接受的维护状态。应根据项目仍能应对相关变化的证据评估维护情况，包括：

- 稳定发布和有意义的源码改动；
- 对有效 issues 和 pull requests 的响应；
- 安全与兼容性修复；
- 对仓库当前 Node.js、TypeScript、browser、framework 和操作系统边界的支持；
- 可识别的维护者与稳定的发布来源。

发布频率本身不等于可靠性。成熟包可能很少需要发布，而频繁发布的包仍可能不稳定或维护不佳。

维护不再可信时应拒绝候选，包括相关安全或兼容缺陷无人处理、包已跟不上受支持的运行时、项目明确停止维护，或无法再确认其维护者与发布来源。

当其他条件可接受的候选在能力、许可证、采用情况和产物影响上相当时，优先选择维护活动更持续、响应更及时的包。

## 决策摘要

以下是硬性准入门槛：

- 依赖具有可证明的必要性；
- 选定版本未被废弃；
- 许可证明确、兼容且可接受；
- 维护状态可信；
- 生产依赖使最终产物增加不超过 30%。

通过全部硬性门槛后，使用以下加权信号比较候选：

- 持续较高的 npm 周下载量提高权重；
- 生产产物增幅为 15% 至 30%（含）时降低权重；
- 其余条件相当时，更持续且响应及时的维护活动提高权重。

如果没有候选通过全部硬性门槛，就不要引入包。应报告未满足的需求和可用替代方案，而不是静默放宽本政策。
