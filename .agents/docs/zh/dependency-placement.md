# 依赖放置与打包

[English](../dependency-placement.md) | [简体中文](./dependency-placement.md)

先遵循[依赖准入](./dependency-admission.md)。本页拥有依赖字段与交付边界规则，不放宽准入门槛，也不授权无关依赖迁移。包分发结构由[仓库架构](./architecture.md#limina-边界)拥有。

对发布的 Limina 工具，优先将能够安全纳入交付产物的私有实现依赖打包。这些构建输入放入 `devDependencies`，即使打包后的代码会在运行时执行。若依赖的安装、宿主兼容性、模块身份、资源或公共类型必须保持为消费者可见合同，则将其 externalize。不能仅凭包体积或源码中的 import 决定字段。

## 按交付合同选择字段

| 依赖角色                                         | 声明                                                              | 交付要求                                                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 构建、测试、lint、文档或其他仅开发阶段使用的工具 | `devDependencies`                                                 | 消费者执行发布入口或解析其声明时，不应需要该包。                                                         |
| 能够安全打包的内部实现                           | `devDependencies`                                                 | 交付所需代码与资源，并处理剩余 external import 和公共类型引用；验证生产构建确实包含它们。                |
| 必需的外部运行实现或声明依赖                     | `dependencies`                                                    | 安装必须提供该包，并保留其外部引用。原生二进制、包相对资源或无法打包的加载方式可以成为选用此字段的理由。 |
| 必须与消费者拥有的宿主、编译器或框架兼容         | `peerDependencies`                                                | 声明支持范围、保持 external，并验证预期的宿主解析和实例合同。                                            |
| 由用户选择的可选宿主集成                         | `peerDependencies` 加 `peerDependenciesMeta[name].optional: true` | 缺失时，无关能力仍可用；仅在需要时加载和校验集成。                                                       |
| 自动安装但可缺失的增强能力                       | `optionalDependencies`                                            | 定义并验证跳过安装或安装失败时的行为：有效回退，或明确不可用的可选能力。                                 |

Peer 可以同时放入 `devDependencies`，供仓库开发和测试使用；这不取消发布态 peer 合同，也不允许打包私有替代版本。不能假定 peer 总需手动安装，也不能仅凭 peer 声明认定实例为 singleton。

`bundleDependencies` / `bundledDependencies` 将依赖包纳入发布 tarball，不等于 JavaScript 模块打包。只有明确的分发需求才能引入此机制，不能用它代替本政策。

## 构建与运行时边界

- **检查实际构建。** 读取受影响包的 manifest、JS 和声明 bundler 配置、包生成 hook 及打包后的 manifest。[核心构建](../../../packages/limina/rolldown.config.ts)中的 `dependencies`、`peerDependencies` 和 `optionalDependencies` 及其子路径共同作为两套 external 规则的输入。其他包须独立检查，包括[迁移包构建](../../../packages/migrate/rolldown.config.ts)。字段变化可能改变运行产物与声明输出，不能仅按元数据调整处理。
- **只在行为保持时打包。** 检查动态 import、`require`、相对原包位置的解析、worker／子进程、原生模块、WASM 和数据文件。Bundler 成功不代表这些路径可用。
- **覆盖剩余 external。** 每个剩余第三方 import 都须有明确交付合同，包括来自已打包传递依赖代码的 import。保留许可证 notice 和[打包代码许可证门禁](./license-policy.md)。
- **尊重未打包入口。** 按实际执行方为私有包、仓库脚本和仅经 `tsc` 输出的代码分类。仅供仓库使用的工具可以使用 `devDependencies`；保留运行时 import 的发布入口需要外部交付合同，除非已验证后续构建会将其打包。

## 公共类型声明

独立于 JS 输出审查发布的 `.d.ts`。若仍引用第三方类型，须提供适当的已安装 dependency／peer 合同，或安全内联所需声明。`import type` 和 JS 打包不会消除声明依赖。按消费者的实际需要分类 `@types/*`，不能按名称判断。

验证缺少可选集成时，不受影响的消费者仍可通过类型检查。`skipLibCheck` 不能修复缺失依赖。复用既有的[声明输出与消费者检查](./technology-stack.md)，分别覆盖各自边界。

## 宿主归属

按 Limina 既有的 [provider 与解析合同](./semantics.md)决定编译器／框架依赖放置，不套用“所有编译器必须打包或 external”的规则。保留消费者选择的版本、实例身份和兼容范围；不能为简化打包而换成私有打包的编译器。

## 可选加载

包管理器不会实现回退。仅在需要时加载可选集成，使无关入口能在缺少它时启动。处理预期缺失或明确支持的加载失败时，不得掩盖任意初始化错误、传递依赖缺失或缺陷。请求的检查需要某个缺失工具时，报告能力不可用或失败；不得把跳过必要检查变成成功。

区分平台选择与能力可缺失。上游可能通过 optional 条目分发平台变体，但仍要求当前平台至少有一个可用后端。先检查 loader，再判断是否存在纯 JS 回退，或能否将 Limina 的必需依赖改为 optional。

## 引入与验收

每项依赖须声明在实际使用它的 workspace package 中。遵循 [workspace catalogs](../../../pnpm-workspace.yaml) 和 [lockfile 工作流](./development-workflow.md#编辑边界)；catalog 名称不决定 manifest 字段语义。不能依赖根级 hoisting、未声明的传递依赖或消费者 workspace 中碰巧存在的工具。

改变声明或交付合同前，记录所属包与用途、所选字段、bundled／external 处理、公共类型暴露、宿主／版本要求和缺失时行为。将重要的平台、安装、体积和许可证成本纳入既有[准入审查](./dependency-admission.md#引入验证与决策记录)，不另建一套流程。

在已授权任务范围内，复用既有 build、声明、package 和 packed-consumer 检查。验证受影响的 JS／CLI 入口、脱离生产者开发环境的声明解析、外部依赖完整性，以及适用的可选依赖存在／缺失路径。在相关受支持环境中验证原生组件／资源行为。同步更新必要的 manifest、catalog、生成的 lockfile、配置和回归覆盖。

明确报告未执行的检查与证据缺口。本政策不授权仅为满足验收步骤而安装依赖、重分类现有依赖，或扩大仅分析任务的范围。
