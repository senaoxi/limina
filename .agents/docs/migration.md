Historical tags must not publish automatically. Release scripts target only the approved `packages/limina/dist` and `packages/migrate/dist` pair with matching names, versions and the shared `limina/v<version>` tag. The migration publication manifest must contain no Limina dependency in its runtime, peer, optional or development fields, and no private workspace or unresolved local protocol. Its non-public `migration-build.json` must match both products’ source/dist versions and the release version; CLI, fresh verifier and renderer resources must exist. Release order remains explicitly core then migrate even without a runtime edge. All workspace-only internal source module mappings are removed from the core publication exports. This is a breaking package surface change: select an unpublished breaking version for both products before release; this local implementation does not bump the source versions or authorize publication. Publication uploads under a candidate npm tag, verifies both artifact integrities, and only then promotes the channel. After a successful upload, an E404 for the new version is polled every five seconds against a five-minute monotonic deadline; each npm request retains its own CLI timeout. Other read errors and an observed integrity mismatch fail immediately. A version still invisible at the deadline leaves channels unpromoted. For a non-latest channel, an established `latest` must remain unchanged. A previously missing namespace has no tags at preflight; npm requires its first version to initialize `latest`, so that case accepts only `latest` equal to the just-published version. No other latest change is accepted, and a latest mismatch is reported separately from a target-channel mismatch. A retry accepts an existing version only when its integrity matches; it never overwrites a published version. Historical changelog entries retain their original links. New entries link to the current Limina repository commits, including rewritten imported commits, without consulting the removed commit map. The immutable imported tag names are retained by the release-owned guard in `packages/gates/src/release/check-tag.ts`, so removing migration reports cannot enable historical publication or deployment.

The current public route, fixed base, Vercel gateway and deployment configuration are owned by [Infrastructure](./infrastructure.md#external-gates-and-collaboration). Project association and deployment authority remain subject to their independent gates. Migration of old consumers remains a separate gated action: migrate old consumers to an approved registry version, honor release age/trust, remove old source and Nx/release ownership, validate the old repository, then redirect any remaining old bilingual documentation routes including assets, query parameters and anchors.

Before publication, rollback means stopping the cutover and retaining the old repository. After publication, roll back consumer versions, documentation routes and workflows separately; do not overwrite published versions, unpublish or force-push history.
