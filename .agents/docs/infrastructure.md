## CI and artifacts

Documentation privacy is checked by `docs:privacy` before and after every `docs:build`, including CI's Build Validation and the separately gated deployment build. The [scanner](../../packages/gates/src/privacy/index.ts) examines both language sources, demo data, public assets and all built files, including HTML, JavaScript, search payloads and any source maps. It decodes common JSON/URL/HTML escapes, inline text/source-map data, compressed output and PNG text metadata. It rejects personal/machine paths, local file links, private hosts, terminal identities and credential patterns; errors report only relative locations and categories. Source-only scans exclude dependency directories and unpublished build/cache directories; the built target is independently required and scanned. This is a bounded pattern guard, complemented by Gitleaks and manual image/link review, not exhaustive secret detection or image OCR. PCR and saved audit prose use the same scanner with opt-in `--context-records`, adding narrow conversation-attribution and private run-identifier checks. Repository-relative source paths, technical evidence dates and product-user concepts remain valid; pattern checks still require semantic review.

The [terminal capture](../../scripts/docs/capture-command-transcripts.ts) removes absolute cwd metadata and replaces the workspace, CLI and runtime paths before terminal rendering, including paths split across PTY reads. The capture workspace must be physically outside docs, including through parent-directory aliases, so raw logs and local links never become documentation inputs. ## External gates and collaboration

[Publication](../../.github/workflows/publish-npm.yml) remains manual and restricted to senaoxi/limina and the Release environment. Registry Logaria is consumed through the dev catalog, so neither the local release CLI nor the workflow requires a migration activation variable. The [release CLI](../../packages/gates/src/release/release.ts) applies ordinary Git, version, authentication and package checks. Local release preparation still defers provenance publication to the manually dispatched workflow; removing the activation variable does not dispatch it or authorize an npm upload. Both publication and deployment runners execute `pnpm run build:tools` before tag checks: their release entry resolves through a compiled gates export, which a fresh dependency install does not build. [Tag checks](../../scripts/release/check-tag-cli.ts) reject imported tags, require the complete public source package names/versions, exact tag checkout and origin/main ancestry. Immediately before publishing, the actual Bash workflow queries the latest main push run of CI, Security and CodeQL for the Git-resolved checkout SHA, rejects missing/pending/failed/cancelled/skipped or mismatched responses, and retains the responses and SHA. A green run on another branch or commit cannot satisfy this gate. The checkout must also equal the dispatch event's `GITHUB_SHA`, which npm uses for provenance; dispatch at the release tag or at main while it still identifies that same commit. Changing checkout alone cannot change the attested event commit. Publication jobs are serialized; Vitest retains the CI two-worker limit. Publication and deployment use native `pnpm audit --audit-level high` before external operations.

[Version planning](../../packages/gates/src/release/shared.ts) preserves an existing prerelease identifier when preid is omitted and defaults stable versions to alpha. Explicit identifiers participate in the SemVer increment; downgrades remain rejected. Interactive prompts show the current identifier; complete versions belong in `--version`. The default npm channel follows the resulting version’s first prerelease identifier, using `next` for numeric or SemVer-range-shaped identifiers. An explicit `--npm-tag` can override the channel, but empty values, encoded characters, option-shaped names and version ranges fail during planning. The [paired boundary](../../packages/gates/src/release/publication.ts) also checks the channel so an invalid tag fails before packing or uploading.

[Workspace checks](../../packages/gates/src/release/release.ts) run build, unit, tooling, integration and required smoke once per release group, then check each package’s version, artifact, release consistency and pack. Direct test:\* scripts avoid rebuilding through the test/smoke wrappers. `--skip-tests` skips only tests; `--skip-build` reuses existing artifacts and skips build and per-package checks without an implicit rebuild. Non-skipped tests and upload-boundary validation remain active. These external release-orchestration contracts do not change product authority/generation/namespace invariants I01–I12.

The publication runner installs npm 11.21.0 and the approved entry point rejects versions outside `^11.21.0 || >=12.2.0`, matching [npm's trusted dist-tag requirements](https://docs.npmjs.com/trusted-publishers/#managing-dist-tags-with-trusted-publishing). Both packages need an existing authorized publisher with publish and dist-tag operations allowed; the dist-tag capability is separately disabled by default. A new package must first exist before its publisher can be configured. These account prerequisites are not enabled by workflow edits, a public package's metadata or a successful `npm whoami`.

[Paired publication](../../packages/gates/src/release/publication.ts) pre-packs both packages, compares immutable registry integrity before any upload, publishes those exact tarballs under a candidate tag, and only then promotes both to the requested channel. It reads channels back and applies the [latest preservation and namespace bootstrap rules](./migration.md). npm operations remain non-atomic: a failed second upload leaves the first candidate available; a failed second promotion can leave split channels after both versions exist. An approved CI attempt retains the actual tarballs plus expected/observed integrity, channel snapshots and failed phase under `.reports/release/npm`; client failure is reconciled with a registry integrity read. Retrying unchanged artifacts skips matching uploads, repairs channels and rejects mismatched immutable content. Failed attempts are not reported as group success. This evidence belongs to the publisher and does not restore the removed general archive-size/per-package SBOM reporting pipeline.

After both npm packages are verified and promoted, the publication workflow directly creates a GitHub release linking the two packages’ shared changelog at the checked-out approved commit, resolved through Git rather than the dispatch event SHA. The local release preview identifies this manually dispatched workflow as the GitHub release owner. It accepts an existing completed release for that tag; drafts and lookup errors fail. SBOM and license reports remain workflow artifacts, with no custom GitHub release attachment pipeline. The release-owned imported tag-name guard remains effective without the deleted migration metadata; moving an imported tag does not make its name publishable.

[Docs deployment](../../.github/workflows/deploy-docs.yml) remains separately manual and gated by LIMINA_DOCS_DEPLOY_ENABLED=1 and Production. It needs a new approved tag, HTTPS DOCS_ORIGIN and independent Vercel credentials/project.
