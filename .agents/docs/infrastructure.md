## Dependencies and security

[Renovate](../../.github/renovate.json) proposes reviewed catalog/lockfile updates without automerge. Peer/engine contracts and independent fixtures are excluded. Checker families, package-manager changes and majors require dashboard approval; Vite 5 stays on its existing line. No second update bot or old postinstall bootstrap is introduced.

Commit validation uses `@commitlint/cli` and `@commitlint/config-conventional` 21.2.3 for the shared parser, rule engine, configuration and diagnostics, and Husky 9.1.7 for hook installation and execution. Repository-specific layout rules remain in the [commitlint configuration](../../commitlint.config.mjs). These root development dependencies belong to the [catalogs](../../pnpm-workspace.yaml) and do not enter either product artifact. The 2026-10-04 [admission review](./dependency-admission.md) found matching MIT licenses in registry metadata, tagged source and distributed packages, no deprecation on the selected versions, identifiable maintained release sources, and compatible Node floors (`>=22.12.0` for commitlint; `>=18` for Husky). npm's September 27–October 3 download counts were approximately 12.9 million for each commitlint package and 44.1 million for Husky, with rising recent seven-day totals. Sources are the [CLI registry](https://registry.npmjs.org/@commitlint/cli), [conventional-config registry](https://registry.npmjs.org/@commitlint/config-conventional), [Husky registry](https://registry.npmjs.org/husky) and their npm download APIs. No dependency-admission, release-age, trust or audit exception was added.

The private [pnpm ESLint adapter](../../packages/eslint-config/src/plugins/pnpm-plugin/index.ts) counts catalog references in parent/version-qualified overrides. Upstream eslint-plugin-pnpm 1.9.1 incorrectly treats the whole selector as the package name; the adapter suppresses only those false unused-item reports and preserves genuinely unused reports. The root duplicate-catalog rule adds `path-to-regexp` alongside the existing Vite allowance because the deployment graph needs both major 6 and 8 APIs. This is a named lint allowance, not an audit, trust or dependency-admission exception. The ESLint owner-boundary regression exercises real temporary workspaces, including a scoped version-qualified selector, and demonstrates the upstream failure alongside the adapted result.

[Dependency review](../../.github/workflows/dependency-review.yml) covers runtime/development/unknown scopes at high severity. Its allowed-license list is maintained in [configuration](../../.github/dependency-review-config.yml) alongside the [bundled-license policy](../../packages/build-tools/src/license-policy.ts); there is no separate configuration synchronization script. The action does not exhaustively reject unknown license metadata; the build plugin separately rejects missing/conflicting/prohibited bundle evidence. Non-bundled dependencies still require admission review.

[Security CI](../../.github/workflows/security.yml) integrates dependency audit, license reporting, directory SBOM generation and a reachable-history secret scan on PR/main/weekly/manual events, following the docs-islands workflow organization. Bash/jq steps directly parse pnpm advisory JSON and fail on process, registry or schema errors; high/critical decisions count returned advisory details after existing exclusions. Reports are retained as workflow artifacts, with aggregate failure/cancellation/skipped states rejected by Security Summary. Gitleaks CLI 8.30.1 retains its official Linux archive checksum and redacted reports. No automatic issue/PR messaging or new audit/trust exclusion is introduced.

## CI and artifacts

Documentation privacy is checked by `docs:privacy` before and after every `docs:build`, including CI's Build Validation and the separately gated deployment build. The [scanner](../../scripts/docs/privacy.ts) examines both language sources, demo data, public assets and all built files, including HTML, JavaScript, search payloads and any source maps. It decodes common JSON/URL/HTML escapes, inline text/source-map data, compressed output and PNG text metadata. It rejects personal/machine paths, local file links, private hosts, terminal identities and credential patterns; errors report only relative locations and categories. Source-only scans exclude dependency directories and unpublished build/cache directories; the built target is independently required and scanned. This is a bounded pattern guard, complemented by Gitleaks and manual image/link review, not exhaustive secret detection or image OCR. PCR and saved audit prose use the same scanner with opt-in `--context-records`, adding narrow conversation-attribution and private run-identifier checks. Repository-relative source paths, technical evidence dates and product-user concepts remain valid; pattern checks still require semantic review.

The [terminal capture](../../scripts/docs/capture-command-transcripts.ts) removes absolute cwd metadata and replaces the workspace, CLI and runtime paths before terminal rendering, including paths split across PTY reads. Public query examples retain runnable workspace-relative commands and interactive frames; output hashes describe that public stream. Capture output is checked before writing. The capture workspace must be physically outside docs, including through parent-directory aliases, so raw logs and local links never become documentation inputs. The [privacy controls](../../scripts/docs/privacy.spec.ts) exercise the capture process boundary, terminal rendering, encoded inputs, nested public files, compressed image metadata and redacted failures. The 2026-10-03 source baseline failed the new guard for recorded personal paths; regenerated Linux recordings passed. No product authority invariant or security exclusion is changed.

Publication integration fixtures use a subprocess-owned clock to advance metadata-poll waits without real sleeps, while retaining real npm requests to their local test registry. This removes the four five-second sleeps behind main's 2026-10-03 Windows process timeout. Existing assertions still require both versions' integrity to become visible before promotion and reject an expired deadline; production polling, timeout limits and manual workflow dispatch are unchanged.

Repository checks use Limina’s [built-in default workflow](../../packages/limina/src/pipeline/steps.ts) through `limina check`, and named pipelines in [limina.config.mts](../../limina.config.mts) through `limina check <pipeline>`. Root scripts, documentation builds and release orchestration delegate fixed workflows to these entry points. The root configuration does not redefine `pipelines.check`; the default retains graph, source, proof and checker validation. Custom pipeline names describe their purpose: `typecheck`, `format`, `lint`, `packages`, `privacy`, `release-tag` and `release`. `typecheck` runs the managed `checker:build` task, which selects and materializes the current TypeScript and Vue graph entries. External command inputs are fixed in configuration under the [CLI workflow boundary](./limina-system-model.md#pipeline-and-phase-contracts). The `docs:privacy` script invokes the scanner directly so its dedicated input contract can accept targets, `--built` and `--context-records`; the fixed `privacy` pipeline remains available for its default scan. Commit message files use a separate integration entry point. The unused `graph`, `lib`, `vue`, `package` and `publish` aliases are removed: the first three manually selected generated checker paths, `lib` used the same tsgo entry as `graph`, and package/release checks now have actual callers. The [root-config integration guard](../../packages/limina/integration/tests/root-config.spec.ts) runs both configured compiler scopes against a small workspace and rejects independent TypeScript and Vue source errors. Product invariants I01–I12 remain unchanged.

The shared build action invokes root `format:check` and `lint:check` aliases, which run `limina check format` and `limina check lint` for read-only Prettier and ESLint validation. The [CI guard](../../packages/limina/src/__tests__/ci-workflow.spec.ts) resolves their configured command steps to enforce read-only flags. Both commands cover the repository; mutation remains explicit through `format:write` and `lint:fix`, which reuse the current `format` and `lint` scripts.

[CI](../../.github/workflows/ci.yml) preserves native platform builds/tests/smoke and isolated Vue tuples. Linux quality reuses the same commit/platform's package artifacts; other environments build/check independently. Explicit build is followed by test:smoke without rebuilding. No path filter, Nx cache or cached .limina state is introduced. CI Status depends on every validation job and rejects failure/cancellation/skipped jobs.

The full matrix's Unit Tests step caps Vitest at two workers through `VITEST_MAX_WORKERS`, leaving capacity for CLI child processes and framework hosts. Isolated CLI fixtures physically copy runtime source while excluding `__tests__` directories; their dependency links, compiler shims and repository boundaries remain fixture-owned. Test selection, security assertions and timeouts are unchanged.

The [license plugin](../../packages/build-tools/src/license.ts) retains bundled-dependencies.json from actual bundler inputs, including bundled development dependencies, and rejects missing/conflicting/prohibited metadata. The security workflow explicitly selects limina and limina-migrate for `pnpm licenses list --prod --json`; this source-manifest dependency report does not replace the bundle license gate. After building both products, the pinned Anchore/Syft action scans the working directory and generates a CycloneDX SBOM under .reports/sbom. The scan is directory-scoped and is not a per-tarball dependency inventory or consumer-resolution guarantee. Raw audit data and Markdown reports live under .reports/security; license data and reports live under .reports/licenses. Custom archive-size, SHA-512 and per-package SBOM reporting has been removed.

Repository reports are separate from the governed .limina namespace. Product invariants I01–I12 and guards remain unchanged; do not generalize I10/I11 to arbitrary reports/external services. Audit/license/SBOM report failures fail the Security workflow. Publication and deployment independently require native dependency auditing. Publication also directly checks the complete CI, Security and CodeQL workflows at the tagged SHA; merge-time required checks remain repository administration.

## External gates and collaboration

[Publication](../../.github/workflows/publish-npm.yml) remains manual and restricted to senaoxi/limina and the Release environment. Registry Logaria is consumed through the dev catalog, so neither the local release CLI nor the workflow requires a migration activation variable. The [release CLI](../../scripts/release/release.ts) applies ordinary Git, version, authentication and package checks. Local release preparation still defers provenance publication to the manually dispatched workflow; removing the activation variable does not dispatch it or authorize an npm upload. Both publication and deployment runners execute `pnpm run build:tools` before tag checks: their private logger resolves through a compiled package export, which a fresh dependency install does not build. [Tag checks](../../scripts/release/check-tag-cli.ts) reject imported tags, require the complete public source package names/versions, exact tag checkout and origin/main ancestry. Immediately before publishing, the actual Bash workflow queries the latest main push run of CI, Security and CodeQL for the Git-resolved checkout SHA, rejects missing/pending/failed/cancelled/skipped or mismatched responses, and retains the responses and SHA. A green run on another branch or commit cannot satisfy this gate. The checkout must also equal the dispatch event's `GITHUB_SHA`, which npm uses for provenance; dispatch at the release tag or at main while it still identifies that same commit. Changing checkout alone cannot change the attested event commit. Publication jobs are serialized; Vitest retains the CI two-worker limit. Publication and deployment use native `pnpm audit --audit-level high` before external operations.

[Version planning](../../scripts/release/shared.ts) preserves an existing prerelease identifier when preid is omitted and defaults stable versions to alpha. Explicit identifiers participate in the SemVer increment; downgrades remain rejected. Interactive prompts show the current identifier; complete versions belong in `--version`. The default npm channel follows the resulting version’s first prerelease identifier, using `next` for numeric or SemVer-range-shaped identifiers. An explicit `--npm-tag` can override the channel, but empty values, encoded characters, option-shaped names and version ranges fail during planning. The [paired boundary](../../scripts/release/publication.ts) also checks the channel so an invalid tag fails before packing or uploading.

[Workspace checks](../../scripts/release/release.ts) run build, unit, tooling, integration and required smoke once per release group, then check each package’s version, artifact, release consistency and pack. Direct test:\* scripts avoid rebuilding through the test/smoke wrappers. `--skip-tests` skips only tests; `--skip-build` reuses existing artifacts and skips build and per-package checks without an implicit rebuild. Non-skipped tests and upload-boundary validation remain active. These external release-orchestration contracts do not change product authority/generation/namespace invariants I01–I12.

The publication runner installs npm 11.21.0 and the approved entry point rejects versions outside `^11.21.0 || >=12.2.0`, matching [npm's trusted dist-tag requirements](https://docs.npmjs.com/trusted-publishers/#managing-dist-tags-with-trusted-publishing). Both packages need an existing authorized publisher with publish and dist-tag operations allowed; the dist-tag capability is separately disabled by default. A new package must first exist before its publisher can be configured. These account prerequisites are not enabled by workflow edits, a public package's metadata or a successful `npm whoami`.

[Paired publication](../../scripts/release/publication.ts) pre-packs both packages, compares immutable registry integrity before any upload, publishes those exact tarballs under a candidate tag, and only then promotes both to the requested channel. It reads channels back and applies the [latest preservation and namespace bootstrap rules](./migration.md). npm operations remain non-atomic: a failed second upload leaves the first candidate available; a failed second promotion can leave split channels after both versions exist. An approved CI attempt retains the actual tarballs plus expected/observed integrity, channel snapshots and failed phase under `.reports/release/npm`; client failure is reconciled with a registry integrity read. Retrying unchanged artifacts skips matching uploads, repairs channels and rejects mismatched immutable content. Failed attempts are not reported as group success. This evidence belongs to the publisher and does not restore the removed general archive-size/per-package SBOM reporting pipeline.

After both npm packages are verified and promoted, the publication workflow directly creates a GitHub release linking the two packages’ shared changelog at the checked-out approved commit, resolved through Git rather than the dispatch event SHA. The local release preview identifies this manually dispatched workflow as the GitHub release owner. It accepts an existing completed release for that tag; drafts and lookup errors fail. SBOM and license reports remain workflow artifacts, with no custom GitHub release attachment pipeline. The release-owned imported tag-name guard remains effective without the deleted migration metadata; moving an imported tag does not make its name publishable.

[Docs deployment](../../.github/workflows/deploy-docs.yml) remains separately manual and gated by LIMINA_DOCS_DEPLOY_ENABLED=1 and Production. It needs a new approved tag, HTTPS DOCS_ORIGIN and independent Vercel credentials/project. The workflow executes the Vercel CLI from the existing private docs workspace while keeping the repository root as its project cwd. The existing CLI version belongs to the dev catalog and frozen lockfile, with the same scoped deployment security overrides; the removed deployment workspace stays removed. The CLI is a docs development dependency and is outside both published packages. The documented canonical public documentation entry is `https://senao.me/repos/limina/`. The docs site keeps its fixed `/repos/limina/` base; an origin enables sitemap generation under that base. The Senao site owns the external gateway to the independent Limina Vercel deployment. Both workflows retain [migration prerequisites](./migration.md); local integration performs no external operation.

PR titles are checked through a metadata-only workflow without PR checkout. Templates collect package/command/cwd/checker/reproduction/actual checks. English contribution/security policies and project-only editor settings are provided, without automatic fixture formatting.

Local commits use the tracked [Husky commit-msg hook](../../.husky/commit-msg), which invokes the dedicated [message-file entry point](../../scripts/git/commit-message.ts) directly with `node scripts/git/commit-message.ts "$1"`. That entry point invokes commitlint with the shared configuration under the [commit convention](../../.github/commit-convention.md). Root `prepare` and `hooks:install` invoke the Husky CLI directly, which configures local `core.hooksPath` as `.husky/_` and provides the hook execution layer. Installation and execution follow Husky’s native `HUSKY=0` opt-out when Husky is available. Generated Husky files stay untracked. The `commit` pipeline uses the current absolute Node executable so Windows passes message-file paths with spaces as one native argument, including linked worktrees. The root `commit:check` alias invokes the same entry point as `pnpm run commit:check <message-file>` for direct inspection with Git cleanup semantics. The runtime message filename belongs to this integration; there is no `commit` pipeline or generic pipeline argument forwarding. Mechanical checks retain the separate 50-character subject limit, lowercase starts, consecutive body bullets, exact separators, breaking footer, revert bodies and the generated same-version release pair. Conflicting conventional line-length defaults and automatic merge/fixup/squash ignores are disabled. Semantic wording remains review-owned, and message files are never rewritten. The [tooling tests](../../scripts/git/hooks.spec.ts) exercise shared commitlint configuration, CLI acceptance/rejection, Git cleanup, real commit rejection with HEAD/index preservation, idempotent installation, explicit opt-out and commit validation in linked worktrees. They run through `test:tooling` in the existing CI matrix; local execution does not establish remote platform acceptance. Product invariants I01–I12 are unaffected.

Administration separately enables Renovate, supported dependency review/code scanning, private security reports, labels, protected environments and required checks. Suggested checks: CI Status, Dependency Review, Dependency Audit, Secret Scan, CodeQL, PR Title. Local files do not enable settings or establish feature availability.

## Validation ownership

Infrastructure uses direct workflow integration patterned after docs-islands, without a separate maintained infrastructure-script layer. Root test:tooling retains bundle-license and historical-tag guards at the [publication boundary](../../scripts/release/publication.spec.ts), alongside paired npm integrity/retry coverage. Tests for the removed TypeScript audit parser and per-package SBOM are retired with their production surfaces. Security command/report behavior now belongs to the workflow; local shell experiments must execute its actual steps, not a second parser implementation. Product invariants I01–I12 are unaffected because these reports and external services remain outside .limina authority. Build/tooling/unit/integration/smoke/typecheck/check/package/lint/format/docs gates remain applicable; local results do not establish Syft/Gitleaks execution on Actions, remote platform acceptance, publication or deployment.

The [release CLI regression](../../scripts/release/cli.spec.ts) enters ordinary preflight without an activation variable for stable and prerelease plans and retains local provenance requirements. The workflow configuration regression keeps manual dispatch, repository scope and the Release environment. These are external publication contracts; product invariants I01–I12 are unchanged.

The [tag CLI regression](../../scripts/release/check-tag-cli.spec.ts) exercises real Git tags, complete public source groups, checkout identity and main ancestry without migration metadata. The [release workflow regression](../../scripts/release/workflow.spec.ts) executes the actual Bash step against a controlled GitHub CLI response and checks that the shared changelog exists at the linked commit; its Bash path is skipped on Windows, where this Ubuntu publication job does not run. [Changelog coverage](../../scripts/release/shared.spec.ts) protects nonempty rendering and retained historical links.

Release regressions also execute the actual exact-SHA Bash gate against success, wrong SHA/branch/event, a mismatched provenance event SHA, pending, failed/cancelled/skipped, missing and failed lookup responses; the approved CLI rejects npm releases without trusted dist-tag support before package operations. The local HTTP registry exercises partial upload/promotion recovery, retained tarball evidence, accepted uploads with failed client responses, acknowledged-but-missing channel updates, immutable mismatch rejection and preservation of `latest` during beta promotion. This fixture proves orchestration, not npm account authorization or a real registry publication.
