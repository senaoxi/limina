# Limina semantic facts

[English](./semantics.md) | [简体中文](./zh/semantics.md)

This page explains how dependency facts are produced and the limits of their capabilities. Entity and relation definitions belong to the [system model](./system-model.md); properties that must not change accidentally belong to [I02–I07](./invariants.md). This page describes the current adapters, without claiming complete equivalence to every version of the upstream checkers.

## Independent Native Evidence contract

**Current implementation:** [Native Evidence v3](../../packages/limina/src/domain/analysis/native-evidence.ts) feeds the Native provider and schema 10. The domain contract carries no Program, AST, Host or execution authority and adds no user API. It retains requests, raw resolutions, Coverage, stops, project relations, compilation obligations, completeness and execution failures. [Publication](../../packages/limina/src/domain/analysis/native-evidence-freeze.ts) copies and freezes JSON data, rejecting compiler handles, mutable collections, accessors and cycles. Production acceptance and version compatibility remain separate gates; wiring the implementation does not establish that those gates passed.

**Coverage proof:** [the index contract](../../packages/limina/src/domain/analysis/native-coverage.ts) requires a universe established by activated entry selection and solution traversal before successful parsing is known. Extends inputs, generated configs and declaration artifacts do not become owners. Closed discovery, current configuration enumeration and verified file identities are required to prove zero or one membership. Unbounded parse failures keep the relevant universe incomplete; only an evidenced exclusion of the target identity limits their impact. Both lexical and canonical membership require current verified identities for the target and member; stale or unavailable identities cannot count as confirmed members. Lexical membership does not skip canonical alias checks. Two confirmed different members prove ambiguity even in a partial index; otherwise incomplete evidence is unavailable. File identity evidence establishes equivalence, not additional scope.

**Compilation proof:** [obligations](../../packages/limina/src/domain/analysis/native-obligation.ts) keep existence, reference structure and declaration availability independent. Proven existence plus unsatisfied structure is `required`; proven existence plus satisfied structure is `already-satisfied`; proven absence is `not-required`; other combinations are `unknown`. Context, raw references and endpoint mappings must match. Missing or stale output does not erase satisfied structure. File existence alone does not establish available output. A resolved target, owner, load attempt or TypeEvidence cannot independently supply the existence proof.

**Phase qualification:** [context contracts](../../packages/limina/src/domain/analysis/native-context.ts) retain actual TypeScript implementation/version, host, roots/options/raw-reference fingerprints, source and coverage versions, toolchain, epoch and collection identity. Pending Native observations can support baseline analysis and ownership selection; framework candidates only support selection. Locking requires a new context and collection, including a TypeScript-to-TypeScript lock. Locked facts must be freshly collected by the selected semantic family. Input, epoch, phase, collection or locked selection-evidence changes revoke current eligibility without changing historical evidence. Ambiguous selection and a second lock are explicit conflicts; the contract has no retry loop or final executable Checker field. These are data/producer contracts, not authentication of arbitrary forged JavaScript objects.

**Physical boundary:** [The Bounded Host](../../packages/limina/src/core/typescript-semantic/native-program-host.ts) applies Coverage before creating a SourceFile: implementation roots expand; declarations with at least one current verified member expand, including roots; every non-root implementation records ownership and stops. Declarations without a current verified member stop normally. An open/partial universe cannot prove unique implementation ownership, but does not revoke a positive declaration membership proof. Core adds no standard-library, third-party, original-reference-output or Bundler-output exemption and does not change the production FileOwnerLookup algorithm. A full Program is not a Native fact fallback; the final Checker owns real diagnostics and emit. Execution observation may use an input-only Program to discover transitive framework consumption without publishing Native facts, obligations, references or execution targets. [Contract tests](../../packages/limina/src/__tests__/native-evidence-contract.spec.ts) and [compiler observation tests](../../packages/limina/src/__tests__/native-program-observation.spec.ts) protect data derivation and physical loading separately.

**Path selection before loading:** [Selection receipts](../../packages/limina/src/core/typescript-semantic/native-path-selection.ts) probe the qualified compiler candidate order against real existence and its actual reference map before SourceFile creation. Coverage withholding cannot select a lower-priority `.tsx` or `.d.ts`. [Load grants](../../packages/limina/src/core/typescript-semantic/native-program-loads.ts) require a true root or a selected request from an admitted source, as well as Coverage. An independently introduced alternative keeps its own ancestry. Late grants and reference-map discovery use fresh bounded passes over identical roots/options/references; no fake SourceFile, root expansion or full Program fallback is used. Missing redirect output may permit the compiler’s ordinary fallback; existing withheld output may not. Unproved occurrences remain scoped unavailable. [Path regressions](../../packages/limina/src/__tests__/native-path-selection.spec.ts) compare target, complete SourceFile set, subsequent requests and relationships. Compiler source classification is separately qualified: a lower declaration loaded through an independent external entry may inherit metadata from the blocked path fallback. That source and its loaded non-root descendants retain raw observations, but affected emission obligations remain scoped unavailable; declaration-only absence proofs and independent roots remain usable.

**Compilation admission:** [Typed prerequisites](../../packages/limina/src/core/build-graph/compilation-prerequisite.ts) join original requests to their own resolution targets and verified complete/unique Coverage in the current locked context registered by the producer, rather than comparing a cached origin with itself. Deserialized or unbound candidates have no runtime projection qualification. Evidence qualification is separate from proven obligation existence: the required-only dependency writer retains its contract, while Admission can qualify necessary unknowns. Projection uses the selected source's semantic/framework capability and the producer's shared declaration-versus-source selection rule, not whichever candidate edge happens to exist. Required, already-satisfied and necessary unknown relations use the same identity and relationship-kind checks. Source config, Checker, actual generated config and current projection all participate in reference identity, including originally already-satisfied obligations. A declaration obligation needs a declaration reference; an endpoint-matching framework schedule cannot satisfy it. A matching reference may discharge candidate risk without rewriting an unknown raw obligation. Source-consuming Svelte/Astro capabilities do not imply that a provider Checker process must run. Execution rechecks the selected scope against actual references; its lifetime and failure rules are owned by [execution admission](./lifecycle.md#managed-checker-execution-admission). [Admission tests](../../packages/limina/src/__tests__/analysis-completion.spec.ts) use real required, unknown and already-satisfied Native evidence, exercise current-context and typed-reference substitution, and preserve the raw state.

## From ownership candidates to a locked context

[checker-ownership-resolution](../../packages/limina/src/core/build-graph/checker-ownership-resolution.ts) performs discovery, root evidence collection, dependency fact collection, and requirements convergence before freezing semantic authority; Vue promotion, build coloring, and finalization follow. [semantic-authority](../../packages/limina/src/core/build-graph/checker-semantic-authority.ts) accepts only explicit, config, root-file, and dependency evidence for a semantic lock. Build-closure, fallback, solution-constraint, and vue-promotion do not rewrite semantics.

Pending discovery uses the native dependency context from [pending-facts](../../packages/limina/src/core/build-graph/checker-ownership-pending-facts.ts). Framework inference accepts only qualified `missing + pending-framework-candidate` facts. During [physical candidate](../../packages/limina/src/core/build-graph/checker-ownership-physical-candidate.ts) bootstrapping, Oxc supplies a physical candidate, but a known framework extension, governed effective membership, a unique config, and a semantic domain are also required to form an ownership requirement. An ordinary TS/resource path does not lock a framework merely because a physical lookup succeeds. Native source requirements support compilation, not framework semantic authority. A physical declaration resolution blocks Oxc bootstrapping independently of type evidence. A specifier that carries a query or fragment, such as `./Widget.svelte?x`, never bootstraps a physical candidate either: without a checker target, Limina has no authority to reinterpret host syntax through Oxc or the filesystem. Vue custom profiles are matched using the owner-registered path after canonical fallback.

A locked [ProjectSemanticContext](../../packages/limina/src/core/project-dependencies/contracts.ts) requires `LockedSemanticAuthority` at the type level. It has a different entry point from pending discovery. Copying authority in a constructor is not complete runtime authentication of an arbitrary forged JavaScript object. Production calls are constrained by the solving flow and type boundary; this must not be described as an unforgeable security capability.

## Native semantic inputs for a project

[The dependency entry](../../packages/limina/src/core/typescript-semantic/index.ts) has one Native discovery authority: [the version-adapted TypeScript observation adapter](../../packages/limina/src/core/typescript-semantic/native-observation-adapter.ts). Requests come from actual compiler inventory, including own ambient modules that bypass resolver callbacks, repeated occurrences, JSX/helper imports, triple-slash references and types/lib. The host preserves raw resolution, options, types, lib and raw references. Ordinary collection calls neither TypeChecker, full semantic diagnostics nor emit. Explicit TypeEvidence requests retain a separate lifecycle.

[Effective roots](../../packages/limina/src/core/typescript-semantic/effective-roots.ts) still come from configuration parsing. A→B.ts→C.ts stops at B in A's physical frontier and cannot add A→C. A→index.d.ts→helper.d.ts→C.ts continues only when each reached declaration has available Coverage; a compilation edge to C additionally requires an independent obligation proof. Declaration membership does not identify a producer.

The existing TypeScript support range remains 5.4–5.9 and 6.0. The narrow adapter uses compiler callback redirect options in 5.4/5.5, the compiler library map and normalizer before 5.8, and paired reference redirect methods before 5.9. Later versions use their exposed Program methods. The actual version and implementation remain part of context identity. [Packed Native smoke](../../smoke/native-compiler.spec.ts) exercises installed peers at each minor floor; future patches and prereleases still require API qualification and are not proven by those samples. Persistent Native DTO reuse retains its existing 6.0.3 capability boundary; other supported versions collect fresh Bounded Programs, without an alternate discovery algorithm.

Unsupported compiler versions or observation APIs produce explicit unavailability/failure, without changing algorithms. JS, virtual configurations and original references do not trigger a Programless fallback. Each cold collection constructs a fresh Bounded Program and then releases compiler handles; this version retains no `oldProgram`. Valid complete DTOs can restore without a Program; invalidated contexts are recollected. Hook counts never establish completeness.

[The obligation adapter](../../packages/limina/src/core/typescript-semantic/native-program-obligations.ts) separates source options from the audited generated-declaration-project rule and retains raw reference/redirect mappings. Resolution, Coverage ownership, loading attempts and type evidence cannot independently create compilation edges. Satisfied reference structure can coexist with missing/stale output; unknown output is not available output. Generated outputs receive independent contexts with actual projected options and references, without replacing source facts.

## Declaration entry governance

[Declaration closure projection](../../packages/limina/src/core/typescript-semantic/native-closure-projection.ts) consumes already collected, physically bounded facts, retaining entries, final occurrences, supporting paths and normal stop reasons. It does not repeat a package-origin admission policy. Relative imports, paths, package imports, public package entries, managed outputs and replacement libraries obey the same Coverage rule; resolution origin explains the result without granting exemptions.

Multiple declaration memberships permit expansion. Implementations require complete uniqueness proof and still stop when non-root. Uncovered input does not automatically create a governance violation. Actual `noResolve` behavior limits loading; successful resolution cannot fill in a missing obligation. `skipLibCheck` grants no permission to delete inputs. Removing the last entry revokes unreachable cycles; independent entries and diamond predecessors retain their provenance. [Declaration regressions](../../packages/limina/src/__tests__/declaration-policy.spec.ts) cover package branches, configuration entries, cycles, alias rebinding and an independent Oracle.

Core visits all trusted qualified entries. Expected Coverage boundaries, confirmed ambiguity, ordinary misses and unknown obligations stop only their branches. Configuration/file/compiler/internal failures carry separate impact scopes, while independent contexts retain evidence. [Analysis outcomes](../../packages/limina/src/core/build-graph/analysis-outcome.ts) distinguish execution, bounded traversal, compilation completeness, Governance and materialization Admission. Governance cannot rewrite raw facts; projection cannot drop denied/unknown relationships and claim completeness. The Core worklist records baseline, selection and locked eligibility/execution separately. Draining all eligible work can complete with unavailable authority; skipping eligible work cannot. Execution failure IDs are distinct from unavailable evidence. Governance denial or a failed output projection changes only the graph transaction, never completed Core work. Admission checks the concrete candidate’s necessary entries and compilation references; unknown evidence outside those prerequisites is not a blanket veto. Completed traversal does not imply determined compilation relations. Candidate prerequisites retain declaration references and framework scheduling separately. An existing qualified candidate relation can discharge the same target prerequisite even while an occurrence obligation remains unknown; absent necessary relations still block admission. Actual collection failures are reported after eligible independent work has drained, without being reclassified as governance violations. Conflicting explicit semantic families make only their affected terminal entries unavailable; same-family checker conflicts remain governance decisions.

Checker ownership retains toolchain and semantic-script failures as execution failures with affected contexts, while preserving independent project evidence; these failures do not become governance violations. Ordinary resolution misses may inform migration reports without failing Core execution. At Coverage boundaries migration keeps relation completeness undetermined and conservatively preserves native references; known edges are not a complete relation set.

## Persistent importer validity

[Bounded context capture](../../packages/limina/src/core/analysis-cache/bounded-context-capture.ts) stores complete compiler inventory, occurrence facts and actual input receipts. Schema 10, Native adapter/domain versions and collection mode jointly reject old Programless success graphs; old caches are neither converted nor deleted. Roots/options/raw references, the configuration universe, current lexical/canonical identity, positive/negative probes, directories, manifest conditions and installation environment qualify restoration. Equal importer text does not prove an old context valid.

[Restoration binding](../../packages/limina/src/core/build-graph/native-cache-binding.ts) joins the graph, validated contexts, raw snapshots and locked ownership facts; cached summaries or owner fields cannot grant themselves qualification. Normal Coverage stops can restore completely. Execution failures, unknown installation evidence, incomplete channels or forged bindings force cold collection. Invalid consumers atomically replace contributions, without joining old success and new failure into a complete graph. Complete Native hits create no Program; cold/changed contexts construct a new Bounded Program and do not promise changed-file-only parsing. See [lifecycle](./lifecycle.md#persistent-native-analysis-cache) and [fresh-process regressions](../../packages/limina/src/__tests__/full-analysis-cache.spec.ts).

[Bidirectional cache checks](../../packages/limina/src/core/analysis-cache/bounded-inventory-validity.ts) require actual Program members to match the source/importer set and join compiler requests with source occurrences to occurrence/fact records one-to-one. Deleted, orphaned or duplicate records cannot obtain completeness through empty sets. Config-level requests do not require source occurrences, and legitimate members without imports remain present. Raw requests and resolutions must also match one-to-one. Store parsing and [context adoption](../../packages/limina/src/core/analysis-cache/context-records.ts) use the same checks, so graph rejection cannot reuse a context with missing facts. A frozen compiler inventory receipt is captured before Program disposal: it binds each raw request to its exact occurrence (UTF-16 range, kind, ordinal and synthetic metadata), the complete SourceFile set, admitted roots and actual loaded-source aliases. Restoration compares consumer projections against that receipt and joins every successful load back to an actual member; matching two truncated projections is insufficient. Redirect targets keep the SourceFile returned by the compiler, without requiring lexical path equality. Missing receipts and old adapter identities require cold collection; recovery never regenerates receipts from cached projections. Only a valid context may survive graph-only rejection. The checks revoke cache reuse only: they do not turn scoped unavailable into execution failure or rewrite completed Core work. Damaged stores follow the existing complete-model cold fallback; direct context restoration preserves independent valid contexts. [Real-store regressions](../../packages/limina/src/__tests__/full-analysis-cache.spec.ts) cover source/occurrence/fact damage inside valid checksum envelopes, recollection, publication and next-process restoration. This does not establish that a normal producer naturally emits such damage.

[Vue analysis records](../../packages/limina/src/core/analysis-cache/vue-records.ts) support physical projects using TypeScript 6.0.3, vue-tsc and language-core 3.2.4, and Volar TypeScript 2.4.27, without custom Vue plugins. Stable identity includes effective options, raw references, source profiles, config closure and toolchain identity, while runtime generation is rebound on restore. Supported preparation facts, mapped resolutions and resource type evidence are validated DTOs queried before acquiring a live Vue context. Query coverage must be complete. Host reads, full manifest content, successful and failed probes, directory/path bindings, generated-script/mapping digests and installation environments form the context receipt. Unobserved directory enumeration and unsupported/opaque results cannot grant completeness. Tool module bytes and bindings are observed afresh per invocation. Vue collections use their existing Vue context for direct-source observations and support inputs, with separate query coverage from resolution and preparation.

The mixed graph requires every contributing native and Vue context to be complete. Its Vue references resolve to current parsed identities; Program, AST, Symbol, callable hosts, plugin objects and artifact authority never enter the DTO. Custom plugins, virtual inputs and Astro/Svelte retain cold fallback. [Vue cache regressions](../../packages/limina/src/__tests__/vue-analysis-cache.spec.ts) cover fresh processes, invalidation, partial records, runtime generation and cache access policy. This is analysis reuse; checker diagnostics and emit still follow checker execution.

## Occurrences, evidence, and graph requirements

The Native flow is actual compiler request → raw resolution → Coverage frontier → independent obligation proof → qualified locked fact → reference projection. No handwritten request list gates Native discovery.

| Request                                        | Native/runtime boundary                                                                                                                                                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| import / export / import type / dynamic import | Preserve compiler occurrences, modes, repeated locations and actual resolution.                                                                                                                                    |
| CommonJS                                       | Compiler-recognized JS require, including its actual shadowing behavior, is Native. Ordinary TS require/createRequire stays in the separate runtime collector and does not automatically create compilation edges. |
| ambient / augmentation                         | Preserve own ambient fast paths. An augmentation resolution does not prove a compilation obligation; unknown status can stop normally.                                                                             |
| JSDoc / declarations                           | Follow actual TS/JS compiler inventory and each declaration's Coverage, without scanning arbitrary comment strings.                                                                                                |
| path / types / lib / JSX / helper              | Preserve separate channels, configuration provenance and real implicit requests; do not delete types/lib or manufacture roots.                                                                                     |

[The runtime source collector](../../packages/limina/src/core/project-dependencies/runtime-source.ts) retains lexical require, createRequire and require.resolve for source/package governance and graph export. Its request purpose, cache identity and output qualification are separate from Native; `referenceRequirement` is null. Graph Check obtains Native targets from [proved obligations](../../packages/limina/src/core/typescript-semantic/native-fact-qualification.ts), without deriving them again from FileOwnerLookup hits.

Graph Check consumes proved uncovered implementation facts through [a separate workspace Governance consumer](../../packages/limina/src/graph-check/native-coverage-governance.ts). Existing source-package policy can report an unmapped/outside-graph import independently of compilation obligation eligibility. Unavailable Coverage and declaration stops do not qualify for that finding; missing or untyped package entries retain their existing runtime-policy finding. This consumer never creates reference edges. The filesystem detector fixtures retain both policy counterexamples and the denied generated reference, which must remain visible in the graph.

TypeEvidence is a separate on-demand type proof and cannot create or erase compilation obligations; the actual Checker owns pure type diagnostics. Complete specifiers, including query/fragment syntax, retain identity, and Oxc cannot repair Native misses. Framework mappings, capabilities and schedules remain owned by their adapters; runtime-use cannot become a Native reference.

JSDoc location binds an existing occurrence to parsed AST nodes, including every adjacent comment block; the public TypeScript tag-ownership helper omits some compiler requests. The [locator](../../packages/limina/src/core/typescript-semantic/source-file-literals.ts) preserves exact UTF-16 ranges and node identity without discovering requests, synthesizing SourceFiles or resolving by specifier alone. Framework type queries rebind detached candidates to the current Program and require that its inventory contains the same JSDoc literal before querying a Symbol. Missing metadata, unmatched or ambiguous ranges remain scoped unavailable; a located compiler miss remains missing, and independent observations survive. [JSDoc regressions](../../packages/limina/src/__tests__/jsdoc-semantic-location.spec.ts) cover the original node:test annotation, repeated occurrences, @import, ignored documentation, noResolve and physical truncation. Cache adapter identities invalidate prior observations; no roots, compiler options, references or discovery authority change.

## Locked resolution and framework preparation

The locked routes in [checker-resolution-provider](../../packages/limina/src/core/import-analysis/checker-resolution-provider.ts) set Oxc to null. A checker miss stays a miss; runtime/resource classification cannot supply a semantic target. This restriction applies to that call chain and must not be expanded into “Oxc never produces evidence anywhere in Limina analysis.” Astro pre-semantic eligibility skips only known virtual specifiers, plain explicit non-source extensions, and Oxc-identified resource targets; query or fragment syntax is not a skip authority, so the complete specifier reaches the Astro adapter and its result is accepted as is.

[PreparedDependencyFact](../../packages/limina/src/core/framework-semantic/contracts.ts) preserves occurrences, mappings, raw resolutions and structural redirect evidence. Native uses independent compilation-obligation proof; framework adapters retain their own requirement decision; a complete observed miss differs from unavailable observation. Pending observations produce dependency-semantics failures and cannot publish a complete graph. A different provider requires attributable checker structure; paths and suffixes never create positive TypeEvidence.

[Framework support contributions](../../packages/limina/src/core/framework-semantic/support-contributions.ts) are collected during complete Astro/Svelte dependency preparation from each adapter's existing Program and resolver. Physical non-root support inputs retain their direct-source provenance; generated code still requires its existing source map. Module imports and legal path/types directives can contribute obligations without becoming roots. Foreign owned implementations retain their own internal analysis. Governance ignores external support targets while retaining workspace targets; declaration JSDoc examples are not compiler occurrences. Resolution-only preparation remains lazy.

The shared contract covers dependency meaning and compilation obligations. Each adapter retains its resolver, virtual mapping and Program lifecycle. Vue-to-Vue relations still select declaration-provider according to capability; Astro/Svelte component relations may select framework-schedule in governance. Limina observes real Project Reference Redirect structure without reimplementing its producer mapping, feeding inferred references back into discovery, or persisting Programs, ASTs or Symbols.

| Family     | Actual semantic channel                                                                                                                                                                                 | Limits that must be preserved                                                                                                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript | Compiler-driven physically Coverage-bounded Program                                                                                                                                                     | Collection preserves roots and eligible support contributions without granting support inputs ownership                                                                                                                                              |
| Vue        | The Vue source profile distinguishes native channels from the Vue host/service script; [resolution](../../packages/limina/src/core/vue-semantic/resolution.ts)                                          | A matching VueSemanticIdentity is required; ordinary native TS occurrences do not all need to pass through an SFC source map. Strict mapping failure cannot be repaired by arbitrarily selecting another mapping segment                             |
| Astro      | Lazy language-service Program, Astro type environment, and generated snapshots in [context](../../packages/limina/src/core/astro-semantic/context.ts); other native channels may use TS                 | Roots, config, and toolchain determine the context; being able to read an adjacent extension is not equivalent to supporting the complete framework checker                                                                                          |
| Svelte     | Leaf-owned svelte2tsx / compiler / TS, with the TS host resolving generated scripts; [module-resolution](../../packages/limina/src/core/svelte-semantic/module-resolution.ts) preserves occurrence mode | Explicit `.svelte` resolution does not pass occurrence mode. A virtual `.d.svelte.ts` maps back to source only when that source exists and no real `.svelte.d.ts` exists; real declarations take precedence, with no second package exports resolver |

The Svelte adapter covers source transformation, the generated host, strict source mapping, and that host's module resolution. It does not load the complete `svelte.config` / preprocess pipeline and cannot promise equivalence to every svelte-check configuration. Native `.ts/.js` files still use native root/fact enumeration. In the generated graph, Astro/Svelte are complete leaf typecheck targets; they do not receive declaration wrappers or transparent build solutions.

Toolchain provenance, accepted versions, and capability checks are defined by the concrete resolvers/runtimes in [checker](../../packages/limina/src/checker) and the framework contexts. An adapter accepting a version range establishes only the code's admission conditions; tests with an installed tuple establish only that tuple's cases. Other minors, Windows, and uninstalled optional checkers still need their own validation.

Concrete tuple owners are [Vue compatibility](../../packages/limina/src/checker/vue-semantic-compatibility.ts), [Astro compatibility](../../packages/limina/src/checker/astro-semantic-compatibility.ts), and the [Svelte toolchain](../../packages/limina/src/core/svelte-semantic/toolchain.ts). Vue resolves Language Core/Volar/TypeScript from vue-tsc; Astro resolves the compiler from the check-owned Language Server. Workspace-root retries must not hide missing leaf dependencies. Paths provide provenance and instance identity, not a pnpm-layout compatibility predicate.

As of **2026-10-01**, Astro check admission uses the shared external-checker contract `>=0.9.6 <0.10.0` and its existing `includePrerelease: true` policy. Language Server, compiler, and Volar retain their exact tuple requirements and internal API shape checks; unsupported combinations still fail closed under [I04](./invariants.md). The [Astro toolchain guard](../../packages/limina/src/__tests__/astro-semantic-toolchain.spec.ts) exercises version and prerelease boundaries, while the [packed consumer guard](../../smoke/consumer.spec.ts) exercises installed `0.9.6` with TypeScript `5.9.3` and `0.9.10` with TypeScript `6.0.3`. These cases do not establish compatibility for every future patch or prerelease.

Svelte [source-mapping](../../packages/limina/src/core/svelte-semantic/source-mapping.ts) requires explicit segments to map every UTF-16 offset of a generated dependency continuously and monotonically to the current source. Partial coverage, cross-source mappings, or discontinuity produce a mismatch; entirely unmapped input remains an unmapped observation. [generated-script](../../packages/limina/src/core/svelte-semantic/generated-script.ts) constructs TraceMap without a map URL to avoid rebasing an absolute Windows source drive again. Vue/Astro use their own mapping algorithms for full-token/inner-content mapping, ambiguity, and mismatch; one framework's map conditions cannot be applied to all frameworks.

Actual consumer occurrences supply package export resolution. Graph check and graph export consume the same retained checker facts; neither builds an eager exports index, tries a second profile, or uses runtime evidence to repair a checker miss. Self-name, conditions and framework mapping follow the selected checker. [Vue guards](../../packages/limina/src/__tests__/vue-semantic.spec.ts) and [Astro/native guards](../../packages/limina/src/__tests__/workspace-export-resolution.spec.ts) use real consumers; Svelte guards use generated component dependencies. Conditional behavior remains toolchain-version dependent.

Native files in a Vue semantic context carry the module format computed by that same Vue-owned TypeScript instance, language-service host, and compiler options. The lazy SourceFile therefore selects the same import/require conditions as the eventual Program for .mts, .cts, and package-scoped .ts files, without constructing the Program just to determine format. [Vue semantic regressions](../../packages/limina/src/__tests__/vue-semantic.spec.ts) compare lazy resolution against the actual checker provider and assert the Program remains lazy.

The default native `tsc` execution uses Node with the `typescript/bin/tsc` entry resolved from the Limina installation, matching runtime dependency preflight and native semantic analysis. Execution-root `.bin` directories and ambient PATH cannot select another TypeScript version. Explicit internal runner command overrides retain their requested command and argument contract. [Command-origin tests](../../packages/limina/src/__tests__/checker-command-origin.spec.ts) verify the installed compiler version without PATH and preserve build/watch and override arguments.

## Configuration projection boundaries

Output target inheritance preserves the TypeScript array order even when sibling branches share an ancestor. The TypeScript configuration parser owns inheritance resolution, cycle diagnostics and effective options. Framework intent reads the actual parsed configuration closure, including package `tsconfig` entries, dotted names and extensionless files; failed parsing cannot silently fall back to a default target. [Compiler target regressions](../../packages/limina/src/__tests__/compiler-target.spec.ts) compare diamond, deep, repeated, reversed and own-override cases with the TypeScript parser.

[Compiler overrides](../../packages/limina/src/core/build-graph/compiler-overrides.ts) preserve the source's actually selected config type-directive entries through [type-input projection](../../packages/limina/src/core/build-graph/type-input-projection.ts). Relative strings are not blindly rebased: a competing `typeRoots` candidate can win source resolution. Direct, inherited, absolute and automatic/wildcard entries retain compiler selection; a source miss cannot become an unrelated generated hit. No extra edge, enlarged root set or removed `typeRoots` hides a mismatch.

`TypeInputProjectionReceipt` proves only `config-type-directives` entry preservation, not the complete type environment or all request relationships. Existing `outputs.target` selection and defaults remain valid. Different default libraries alone are not an error. The separate [output projection](../../packages/limina/src/core/build-graph/output-projection.ts) checks that actual output governance dependencies are covered by existing output relations; uncovered or unobservable inputs report a capability limit with their source chain. It does not expand the source graph or infer arbitrary declaration producers. Fresh-process restoration checks type-entry preservation and output validity separately. Type-entry selection and proof queries use the same observed resolution cache; graph receipts retain the queries used to choose generated entries so a later local change can reuse them after a clean restore.

Vue output projection reuses the existing `vue-tsc` / Vue Language Core / Volar provider and shared declaration-closure policy. A [separate output identity](../../packages/limina/src/core/vue-semantic/output-identity.ts) retains the source's roots, profiles, configuration closure and toolchain while applying effective output compiler options. Both native files under a Vue owner and mapped SFC dependencies are recollected through that provider; different source/output targets are allowed, but every governed output requirement must already have an output reference. Missing identity, unsupported observation and uncovered dependencies still fail closed. [Generated graph regressions](../../packages/limina/src/__tests__/generated-graph.spec.ts) exercise both target directions with real `vue-tsc -b` output and an independently removed output relation. No dependency or second framework resolver is introduced.

An inferred reference can point forward to a declaration that a subsequent ordered `tsc -b` will create. This permission does not require successful pre-build Checker diagnostics or an existing output, and does not permit stale output to become discovery evidence. Generated configs cannot establish source checker authority.

At the governance layer, source type leaves may not contain handwritten `references`; the [config reader](../../packages/limina/src/core/build-graph/generated/config-reader-basics.ts) rejects that shape. Solutions aggregate projects, and `implicitRefs` records explicit dynamic/virtual relations. The lower-level semantic context supporting raw references does not relax the governed leaf shape. [generated-configs](../../packages/limina/src/core/build-graph/generated-configs.ts) points declaration outDir/declarationDir at the same managed dts root to prevent inherited output redirection. It overrides `rewriteRelativeImportExtensions` only when enabled in effective source config, avoiding unconditional introduction of an option older compilers do not recognize. Supported solutions have no outputs.

Managed-output lookup may explain an explicitly managed output, but does not turn declaration consumption into a source relation. Locked ownership and coloring retain qualified resolved implementation requirements; a real reference redirect cannot promote the consumer's checker. Framework scheduling uses eligible source requirements and existing checker capabilities. When changing these boundaries, check [I03–I07](./invariants.md) together, including actual generated-config builds rather than resolver hits alone.
