## Limina boundary

Repository security/reporting and external workflow boundaries are owned by [infrastructure](./infrastructure.md). The build plugin's bundled inventory is a publication asset, separate from Limina's governed artifact namespace.

The private root `@limina/monorepo` orchestrates commands and shared tooling. Within this monorepo, `packages/limina` owns the public core package, `limina`; its `src`, `bin`, `schemas`, `fixtures` and `integration` retain their internal organization. The second public package, `limina-migrate`, lives in `packages/migrate`. Only their generated `dist` directories are publication targets. The migration package uses `limina` only as a workspace development dependency and embeds the required current-source core implementation at build time. Both products still share one release version; published migrate has no Limina dependency, peer or optional dependency. Its own runtime dependencies and capability peers are explicit. The core has no runtime dependency on the migration package. Workspace packages consume `limina/internal/*` source modules. The `flow`, `core`, `utils` and `check-reporting` directories use wildcard mappings; other entries are explicitly mapped. All targets point directly to current `.ts` source files. The single-file `limina/internal/flow` entry maps separately to `src/flow.ts`. These same-release entries are workspace-only; the core publication hook removes `./internal` and every `./internal/` mapping while retaining normal workers, public API, types and schema. Migrate resolves the source modules through this export map and embeds them without a migration-specific aggregate entry. The CLI-only migration package runs publint and runtime boundary checks; its installed CLI is covered by tarball smoke tests. The core retains ATTW for its TypeScript API. Field selection and delivery validation follow [dependency placement and bundling](./dependency-placement.md).

The other private workspaces are `docs`, `smoke`, `packages/build-tools` and `packages/gates`. The private `@limina/gates` owns repository license, commit, privacy, release and ESLint checks; root scripts and configurations delegate to its explicit entries. See [repository gates](./gates.md). Fixture repositories retain independent workspace manifests and lockfiles and are outside the main workspace. Gates bootstrap through TypeScript before build tools, without invoking Limina. Rolldown then builds the product before governance and consumer checks. Toolchain and dependency versions are recorded in [technology-stack](./technology-stack.md).

Root release scripts, the product and build-tools consume registry Logaria through the dev catalog (`^0.0.4`), locked to 0.0.4. No sibling Logaria build is required. The package generator resolves the catalog through pnpm and rejects unsupported local protocols.

The independent migration package preserves the existing migration transaction and governance semantics. The old `limina migration` command forwards to a local matching package or downloads that exact version through npm. Both packages share one version, release group and `limina/v<version>` tag. See [migration status](./migration.md) for evidence and the independence gate, and [Limina architecture](./limina.md) for product invariants.

The Vercel deployment CLI is a development dependency of the existing private `docs` workspace, resolved through the dev catalog and frozen lockfile. It does not join the two-package publication group; see the [infrastructure owner](./infrastructure.md).

## Implementation cohesion and boundaries

Organize implementation around a capability and its state lifetime. Types, constants and helpers used only by that capability can live beside its implementation; a separate file needs a readable responsibility, a stable interface, an adapter/process boundary or genuine reuse. File length and caller count are review signals, not independent reasons to split or merge. Direct package-internal imports are appropriate when a barrel adds no boundary. The [ESLint policy](./gates.md#eslint-structure-policy) leaves these decisions to responsibility review.

| Area                     | Cohesive implementation and retained boundary                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Core analysis            | Build-script parsing, workspace export expansion, source-config collection, coloring, generated config readers, Knip preparation, TypeEvidence orchestration, Native closure projection and the tagged cache codec own their local helpers. Source-config discovery and Coverage remain independent from successful collection. Semantic authority, execution ownership, source ownership, coverage, compilation obligations and cache restoration qualifications remain separate concepts and owners. Framework/compiler adapters and observed-input readers retain their boundaries. |
| Runtime and presentation | CLI option parsing, execution setup/run, scheduler readiness, flow-task completion, checker-host pending requests, dependency-plan construction, config-observation diagnostics and local checker resolution stay with their owners. Scheduler settlement, generation control, managed mutation, output publication and rendering state have different lifetimes. Checker host, renderer and migration-verifier process entries retain source/bundle resolution and resource ownership.                                                                                                |
| Checks and reporting     | Source and graph phase orchestration, dependency graph collection/edges/model, built-in rule predicates, the ATTW adapter, one package-entry run and one check recorder colocate their local operations. Detector domains, Knip/process adapters, proof dimensions, archive cleanup and atomic report publication retain independent responsibilities. A dependency graph document is an observation, not an execution plan.                                                                                                                                                           |
| Migration                | Planning, membership rewriting, JSONC/config edits and per-invocation group execution keep local state and helpers together. The transaction entry directly owns prepared-plan execution and write-policy dispatch. Declared-reference provenance, semantic comparison, output adoption, prepare/apply/rollback, fresh-process verification and audit publication remain distinct stages and authorities.                                                                                                                                                                              |
| Repository tooling       | Gates and build-tools retain explicit package entries; root scripts remain command/CI adapters. Documentation capture, terminal interpretation, playback and visual components keep their own responsibilities. Smoke cases remain installed-consumer boundaries.                                                                                                                                                                                                                                                                                                                      |

The package imports and workspace-only exports above remain the cross-package access contract. Colocation does not widen public exports, extend cache lifetime, move instance state to module scope or change initialization, error, Promise or disposal semantics. The [architecture workflow](./architecture-workflow.md) owns that review; structural acceptance must also follow the [development workflow](./development-workflow.md#validation-and-handoff).

## Distributable agent skill

[`skills/limina`](../../skills/limina/SKILL.md) owns the installable consumer skill. It is separate from `.agents/skills`, which contains repository maintenance procedures. The skill was adapted from [docs-islands at `1e79a5859ec667e86ceea83fa28c04b9f6bf9ed8`](https://github.com/senaoxi/docs-islands/tree/1e79a5859ec667e86ceea83fa28c04b9f6bf9ed8/skills/limina); its standalone license preserves the upstream MIT notice. This is a source migration, not a claim of remote installation or publication.

The entrypoint keeps task selection and essential boundaries; the five references cover configuration, CLI workflows, ownership, package checks, and diagnosis. Examples follow the accompanying source, while operation in another project must use that project's installed version, help, public declarations, schema, and matching source. The skill does not require a Limina checkout, impose pnpm on consumers, expose internal imports as public API, or authorize upgrades and publishing.

When commands, config, checker support, root discovery, caching, or package behavior change, update the relevant skill reference alongside its source owner. Keep it a task guide rather than another exhaustive schema or issue-code catalog. [Init's install command](../../packages/limina/src/commands/init/shared.ts) and both [English](../../docs/en/cli.md) and [Chinese](../../docs/zh/cli.md) CLI guides point to `senaoxi/limina --skill limina`. Existing [init tests](../../packages/limina/src/__tests__/init.spec.ts) cover the accepted installation command and the skipped-install message; prompt refusal and install failure remain separate cases. Skill migration changes this installation destination, not governance identity, relations, or cache lifetimes.

## Documentation command output

The homepage uses `HomeFeatures.vue` for feature navigation, `CommandTerminal.vue` for command output and controls, and `use-command-playback.ts` for playback state. Component filenames name their responsibility; command options and their indices use command terminology in props, data attributes and styles. English and Chinese labels share the same recorded CLI output. The full-output disclosure stays open when selecting another command or feature group so readers can compare outputs. Its reading area has a fixed height for the current viewport: changing transcript length must not change the sticky console height and feed back into scroll-driven feature selection. Output retains its printed columns and scrolls horizontally on narrow screens.

[Command recordings](../../docs/.vitepress/theme/command-transcripts.json) are generated by [the capture script](../../scripts/docs/capture-command-transcripts.ts) from a freshly built CLI in an isolated two-package pnpm workspace. Run `pnpm run build`, then `pnpm exec tsx scripts/docs/capture-command-transcripts.ts <new-workspace>`; use a new directory under `~/Project/dev-server-repo/repros/` for verification. Capture requires Python 3 and a POSIX PTY. Optional arguments select the output JSON and an explicit pnpm executable when a system proxy wraps pnpm. The script refuses existing workspace directories, removes parent workspace bin settings, generates a lockfile and runs `pnpm install --frozen-lockfile --offline` against local dependencies. pnpm creates the workspace links and executable shims; its default dependency verification remains enabled. Displayed and executed commands are the same `pnpm exec limina ...` invocations. The recorded JSON is included in the docs TypeScript project. The release pipeline runs from `packages/core`, whose build produces the package manifest and outputs required by package/release checks. The boundary failure uses a cross-package relative source import.

The 2026-10-03 recordings use the default interactive terminal branch: stdout/stderr share a real 100-column, 80-row PTY, `TERM=xterm-256color`, with CI and color overrides unset. [Terminal frame extraction](../../scripts/docs/terminal-frames.ts) interprets cursor movements, erasures and wrapping with xterm rather than concatenating stripped redraws. Writes separated by at most 20 ms are observed together; raw captures remain in the capture workspace. Frames crop unused outer viewport padding and retain internal blank rows, indentation, report borders, diagnostics and invocation queries. Playback replaces the previous screen, using recorded frame intervals after command typing; the full-output disclosure shows the final terminal screen. The UI identifies interactive recordings and their dimensions. Counts, timings, wrapping and local query paths describe that workspace/run. Source, CLI and raw-output hashes plus toolchain versions are retained. Refresh recordings when CLI output changes; this documentation contract does not change product invariants I01–I12 or establish Windows, other terminal-size or deployment parity.

`@xterm/headless` 6.0.0 is a capture-only development dependency for interpreting VT terminal state. A local escape-stripping routine cannot preserve redraw semantics; an informal VT parser would add a standards-maintenance burden. Admission on 2026-10-03 found a consistent MIT license, no registry deprecation, a stable 6.0.0 release from the maintained xterm.js project, and npm adoption of 2,001,724 downloads in the preceding week and 6,573,679 in the preceding month. Its buffer API is experimental; the exact version is pinned and upgrades require the terminal-control reproductions and fresh CLI capture. The selected package has no runtime dependencies and is imported only by the capture script, outside the docs/client and published CLI entry points. Production artifact size thresholds therefore do not apply to this dependency; the recorded frame data still needs the normal docs build and browser checks.

## Documentation sidebar

The article sidebar adapts the existing VitePress components through [reading.css](../../docs/.vitepress/theme/styles/reading.css), retaining the warm light/dark palette in [reading-tokens.css](../../docs/.vitepress/theme/styles/reading-tokens.css). Selected and ordinary links share row insets so selection does not shift text; soft backgrounds and font weight indicate selection, while spacing separates groups. Existing VitePress navigation, folding, history and mobile menu behavior remain the interaction owner; this visual adjustment needs no additional package or navigation implementation.

Closed mobile sidebars are hidden so their controls stay out of keyboard navigation. Mobile links and folding controls retain at least 44px targets. Keyboard focus has an outline, and forced-colors selection uses the system Highlight outline because background colors alone do not survive that mode. Browser acceptance must cover both languages, long labels, breakpoint edges, scrolling, folding, navigation/history, mobile opening/closing, keyboard focus, reduced motion and forced colors; formatting, type checks and documentation builds do not establish these interaction results.
